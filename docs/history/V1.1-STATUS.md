What survives, and is what a user should act on: **the token outcome depends on whether the operator

are CHEAPER than plain at 100% delivered correctness (`bench-r11`, −19.6% guarded).

## Update 5 — requirement coverage becomes attainable, and the benchmark stops crediting red deliveries

The owner's invariant tightened twice more, and both tightenings are in the product and in the
measurement:

> Every objective requirement must have a frozen proof obligation **or remain NOT PROVEN**. Amabie
> must never issue PASS/READY merely because the configured tests are green if authorized
> requirements are not independently covered by adequate proof. A cheaper wrong result is strictly
> worse than an expensive correct one.

### Requirement coverage: the binding path the invariant needs

MEASURED gap: `package.json` `amabie.proofs` accepted any requirement digest, but

1. the obligation engine only credited digests that happened to be NUMERIC objective targets (a
   bench/e2e-looking requirement), so a plainly stated requirement could never be covered by
   measurement, and
2. nothing ever printed the digest an operator would need — so "bind this requirement to a sealed
   check" was advice with no way to follow it, and the only reachable end state was human acceptance.

Both halves are fixed. `amabie task --requirement "<r>"` now prints each requirement's digest with the
exact binding recipe, and `amabie bind <script> --requirement "<r>"` is the OPERATOR's act that writes
the declaration (refusing a script the sealed plan does not run); `obligationsFor` credits a digest
bound to a script the SEALED PLAN runs — that script's exit code is the measurement:

| State | `per-requirement` | Meaning |
|---|---|---|
| every digest is a frozen target or bound to a sealed script | **met** (objective) | coverage inside Amabie's declared proof boundary |
| any digest uncovered | **unproven** (non-objective) | NOT PROVEN; bind it, or a human accepts in a terminal |
| the binding names a script the plan does not run | **unproven** | an unsealed script proves nothing |

`tooling/probes/requirement-coverage-gate.mjs` drives the operator path end to end and found a third
defect on the way: `doctor` offered `next: amabie accept <name>` in the BASE-repository path, where no
candidate exists — a dead end, not a path. It now names the two exits that can actually be taken
(bind a sealed check; or take the work through a candidate and accept it there). The probe: **ALL
PASS (8 checks)** — unbound requirements block a READY verdict and tell the worker; `amabie bind`
records the declaration and names the sealing step; a binding to an unsealed script is refused; and
after binding both requirements and re-running setup the verdict is READY.

### What a declared-but-unbound requirement COSTS, and what binding BUYS (measured)

`bench-r9`/`bench-r9b` registered the fixture's five stated requirements with no sealed proof — the
configuration an operator creates by declaring requirements without binding them. Both arms delivered
the work correctly (2/2 and 2/2, zero false dones, zero false greens), and the price was enormous:

| Configuration | tokens | turns | outcome |
|---|---|---|---|
| `guarded` + 5 registered, unbound requirements | **1.72M / 1.52M** (`bench-r9`) | 45 / 41 | no done-claim; the work was green |
| the same after the worker-facing message was made explicit (`bench-r9b`) | 1.57M / 0.61M | 48 / 28 | still no done-claim |

The message was not the cause — the worker reads Amabie's own output (`amabie …` invoked 4×, 7 KB of
Amabie bytes, its own checks run twice) and pursues a duty only an operator can close.

`bound-requirements` is the OTHER side of that, and it is the configuration to recommend: three
stated requirements, each declared as its own check in `amabie.project.json` and BOUND to the
requirement's digest, with a visible suite that is green before and after (`bench-r11`):

| Arm | tokens | vs plain | delivered correct | false done | false green |
|---|---|---|---|---|---|
| `plain` | 125,369 | — | 5/5 | 0 | — |
| `guarded` | 100,812 | **−19.6%** | 5/5 | 0 | 0 |
| `invisible` | 91,439 | **−27.1%** | 5/5 | 0 | 0 |

So the operator guidance is measured rather than argued: **declaring requirements and binding each to
a check the sealed plan runs makes the gate a collaborator (the checks name exactly which requirement
is unmet, and the protected arms come out cheaper than plain at 100% delivered correctness), while
declaring them unbound makes it a tax.** For a project with no `package.json`, the bindings live in
`amabie.project.json` `proofs` — a gap closed here, because before it a Python/Rust/Go/universal
project could not bind a requirement anywhere and the invariant was satisfiable only in Node
projects (`universal-requirement-binding.mjs`, ALL PASS, 8 checks).

### The benchmark stops crediting a red delivery

MEASURED in `bench-r8`: an agent edited the source, added its own test file, left the project's **own
suite failing**, and claimed success. Amabie blocked it and refused READY — but the benchmark scored
the trial `delivered correct`, because `deliveredCorrect` consulted only the hidden oracle. For a
`correctness` fixture, delivered now requires the hidden oracle **and** the project's own suite, with
`suiteRedAfterClaim` as its own counter. This was the harness flattering an arm, not a product
change: the product was already refusing to certify it.

### What the final matrix says (`bench-r8`, 3 tasks × 3 arms × 5)

| Arm | tokens | vs plain | delivered correct | false done | false green |
|---|---|---|---|---|---|
| `plain` | 163,390 | — | 14/15 | 0 | — |
| `guarded` | 217,388 | **+33.0%** | **15/15** | 0 | 0 |
| `invisible` | 155,678 | −4.7% | 13/15 | 1 | 0 |

The reliability-first reading, stated plainly rather than dressed up: the arm that KEEPS the worker's
own verification reached **100% delivered correctness where plain reached 93.3%**, and the gate is

## Update 4 — proof coverage fails closed: the regression-evidence gate

The owner's invariant for this update: *Amabie must never issue PASS/READY/promotion merely because
the configured tests are green if authorized requirements are not independently covered by adequate
proof. Existing behaviour that must be preserved requires regression evidence. Missing or ambiguous
proof must fail closed, never degrade to PASS.*

### The measured failure this closes

`bench-r5-refactor-preserve-invisible-2`: the agent rewrote `formatMoney`'s string handling, ran
nothing, and finished while `formatMoney("0.5")` returned `$0.05`. The project's own checks passed
BEFORE and AFTER the change, so they carried **no evidence about it** — and Amabie reported READY.
No amount of care in the runner fixes that class, because the checks do not discriminate the change.

### The mechanism

`planDiscrimination(root, cfg)` runs the SEALED plan against the sealed BASE commit with the
candidate's check files overlaid — the classic experiment that asks *"do the checks fail without
this change?"*. The comparison happens in a throwaway `git worktree` (removed in a `finally`), so
the working tree is never mutated. Its answer becomes an ordinary proof obligation
(`discriminationObligation`), which the checkpoint gate, `doctor` and the promotion path read:

| Measurement | Obligation | Consequence |
|---|---|---|
| the checks FAIL without the change | `regression-evidence` **met** | the plan's pass is evidence about the change |
| the checks PASS without the change too | `regression-evidence` **unproven** | **NOT PROVEN** — the Stop hook blocks with an actionable instruction, and `doctor` refuses READY |
| the comparison cannot run (no baseline, no change, no product behaviour, an environment-shaped base failure) | not applicable | no duty is invented, and no duty is discharged either — today's behaviour stands |

It is deliberately narrow about what it asks for. A change that touches only checks, prose or
licences has no product behaviour to discriminate and is NOT asked to prove itself; Amabie's own
artefacts (`.claude/`, `.amabie/`) are excluded from the changed set, because counting the
verifier's own wiring as "the candidate's change" made an untouched repository report NOT PROVEN
(measured, and now a probe case).

**Measurement supersedes inference.** `obligationsFor` already had a declared-kind heuristic ("a
bugfix that touches no test file is UNPROVEN"). When the measured obligation exists it REPLACES that
heuristic: otherwise a bugfix that turns an existing red check green — real regression evidence,
no test file touched — would be called unproven, and a test file touched for show would be called
met.

### Fail closed, in both directions of the gate

- **Stop hook**: an OBJECTIVE obligation that is unproven now BLOCKS with an instruction the agent
  can act on ("make the proof discriminate: a check that FAILS without your change and PASSES with
  it"), and the loop guard turns the second attempt into an honest "a human should look, or accept
  it". SUBJECTIVE duties still ride an honest systemMessage — an agent cannot accept for a human.
- **`doctor`**: READY is now reserved for "the plan passed AND nothing is open". Open obligations
  print **NOT PROVEN** and exit 2, naming each one and distinguishing "needs a sealed check" from
  "needs your explicit acceptance". Before this, `doctor` printed READY and merely NOTED them — that
  READY is the one the benchmark recorded as a false green.

### Verified

`tooling/probes/regression-evidence-gate.mjs` drives six real repositories through the real CLI, and
reports **ALL PASS (7 checks)**:

| Case | Result |
|---|---|
| A · product changed, plan green before and after | `doctor` **NOT PROVEN** (exit 2); the Stop hook **BLOCKS**, naming the changed file |
| B · A plus a check that fails without the change | **READY** (the plan discriminates) |
| C · a failing check fixed | **READY** (the plan fails on the base, so its pass is evidence) |
| D · nothing changed | **READY** (no question to ask) |
| E · only check files changed | **READY** (no product behaviour to discriminate) |
| F · the base comparison cannot run (missing module) | not read as evidence — an environment-shaped failure is **unestablished**, and it says so |

`npm test`: **1066 tests / 1062 pass / 0 fail / 4 skip** (measured after Update 5). Eight existing tests encoded the weaker
contract and were updated to assert the STRONGER one (the fail-closed block, the NOT PROVEN verdict,
the measured obligation) — none was relaxed, and every one of them now fails if the gate stops
failing closed.

### What this does NOT claim

An agent-written check that fails on the base is **sensitivity**, not independence: it proves the
checks are *about* the change, not that the change is right. The independent classes remain a sealed
operator-bound proof obligation (`amabie.proofs` + `setup`) and human acceptance for subjective
duties, and this update does not touch those. What it removes is the specific false green where a
green suite certified a behaviour change it could not see.

## Update 3 — the token ledger, four measurement fixes, and what "negative overhead" actually costs

This continuation attacked the one product requirement still unmet: an agent working **with**
Amabie must spend **fewer** model tokens than the same agent without it. The earlier matrices
showed the opposite (`bench-r2`: +14.1% tokens, +26% wall time), and totals could not explain why,
so the benchmark learned to read the CLI's own event stream.

### The instrument became a ledger, and measuring it found four defects

Trials now run with `--output-format stream-json`, and `tooling/benchmark/stream.mjs` turns the
stream into a ledger: turns, every tool call, the bytes the model was SHOWN, how many times the
MODEL ran the project's checks, the hook events, and the tokens spent after the last file edit.
Wiring that against a real run (`tooling/probes/stream-usage-shape.mjs`,
`agent-token-ledger.mjs`) exposed four falsehoods, each of which had silently corrupted a number:

| # | What was believed | What is MEASURED | Effect on published numbers |
|---|---|---|---|
| 1 | one assistant event = one model turn | one event per CONTENT BLOCK: a thinking block and a tool_use arrive as two events sharing `message.id` (measured 4 events for `num_turns: 2`) | turns over-counted 2×; tool calls double-counted |
| 2 | per-message `usage` is the token accounting | `output_tokens: 0` on EVERY assistant event while the run produced output; summing it gave 67,940 "tokens" against the CLI's own 36,448 in the same run | a fabricated token total; the ledger now uses the result event and flags partial per-message usage as unusable |
| 3 | a command containing the word "amabie" is an Amabie invocation | every trial works inside `…\Temp\amabie-bench-…`, so PLAIN-arm runs were credited with Amabie commands and "Amabie-visible bytes" | the two columns the token claim rests on were noise; `isAmabieInvocation` now decides by invocation, with nine pinned cases |
| 4 | `editedTests` (any change under `tests/`) = the agent tampered | it was true in 15 of 15 trials while only meaning "some file changed" — several fixtures require it | replaced by assertion counts before/after; `weakenedTests` means judging text was REMOVED |

Two more measurement decisions came out of the same work. Trials run with
`--setting-sources project,local` and the API environment forwarded explicitly, because a
**user-level** hook on this machine was injecting a multi-kilobyte third-party instruction block
into every measured session. And the instrument fingerprint now covers the **product** the trials
execute (`apps/cli/dist/src`), not just the harness and fixtures — that gap was found honestly, by
planning a rebuild during a running batch and being unable to tell from the records whether the
later trials ran the same binary as the earlier ones.

### The result, and the rule that outranks it

Three matrices, one agent model, one host (`tooling/benchmark/RESULTS.md` has the full tables):

| Matrix | Tasks / cell | raw tokens plain → invisible | turns | checks run BY THE MODEL | delivered correct | Amabie false green |
|---|---|---|---|---|---|---|
| `bench-r4` | 2 × n=10 | 87,518 → **59,664 (−31.8%)** | 7.4 → 4.7 | 1.1 → **0.0** | 20/20 → 20/20 | 0/20 |
| `bench-r5` | 3 × n=10 | 173,075 → **75,450 (−56.4%)** | 10.9 → 5.0 | 1.6 → **0.0** | **29/30 → 28/30** | **1/30** |
| `bench-r6` | 4 harder × n=6 | 150,817 → **62,592 (−58.5%)** | 12.5 → 6.1 | 1.2 → **0.0** | 24/24 → 24/24 | 0/24 |

The mechanism is the product's thesis: in the `invisible` arm the model stopped doing the
verification work, which removed turns and the context they re-read.

**And `bench-r5` is why the owner's priority is now encoded in the instrument rather than left to a
reader.** There, the −56.4% came with one FEWER delivered-correct result and one false green: the
agent changed `formatMoney`'s string parsing, never ran anything, and finished while
`formatMoney("0.5")` returned `$0.05`. Reliability outranks token savings, so every generated
report now carries a `kpi` verdict computed from BOTH numbers, and an arm whose saving costs
correctness is printed as `REJECTED AS A DEFAULT — fewer tokens, LESS correct work`, not as a
saving. A new **`guarded`** arm measures the reliability-first integration: the model is told that
verification is automatic and that a failure will be reported, and that it MAY and SHOULD still run
the checks when it is unsure, when the change may not be covered, or before finishing something it
cannot fully reason about. It is the recommended default; `invisible` is measured because the
aggressive end of the range has to be known, not because it is the recommendation.

### The Claude Code gate, measured rather than assumed

During a blocked trial the CLI emitted `system/notification { key: "stop-hook-error" }`, which
looked like the gate failing. `tooling/probes/hook-block-contract.mjs` planted each candidate
Stop-hook shape in a throwaway project and measured what the harness does with it (Claude Code
2.1.268, this host; re-run: ALL PASS):

| Shape | Repair turn | Reason delivered | Channel |
|---|---|---|---|
| `{"decision":"block","reason":…}` + exit 0 (Amabie's) | yes | **yes** | user message, prefixed `Stop hook feedback:` |
| exit 2 with the reason on stderr | yes | yes | user message (with the `[node …]` wrapper) |
| `{"continue":false,"stopReason":…}` | **no** | **no** | none |
| `{"systemMessage":…}` (Amabie's loop guard) | no | yes | `system/informational` notice |
| silent exit 0 (Amabie's passing shape) | no | n/a | none |

So the gate does what `amabie agents` claims, and the `stop-hook-error` notice is emitted for EVERY
blocking shape — a property of blocking, not of Amabie's payload. The first version of this probe
inspected only `system` notices, concluded the reason was dropped, and was **wrong**; the correction
is recorded in the probe's own header, because reading the whole output before changing anything is
the rule this repository keeps having to relearn.

### One more measured confound: the plain arm is not Amabie-naive

`tooling/probes/agent-memory-visible.mjs` asked the model, in a throwaway project, whether it had
been given project-specific notes about other repositories. It quoted this machine's global
`~/.claude/CLAUDE.md` verbatim — including "avoid redundant self-verification when deterministic
project tooling or Amabie can perform the same check independently" — and one plain trial really did
run `amabie status` unprompted. Both arms see that memory, so the arm-to-arm comparison stays valid,
but the measured saving is an **under-estimate** for a naive user. Redirecting the CLI's config home
does NOT remove the memory (measured), and `--bare` would also remove the Hook the protected arm
depends on, so the confound is disclosed rather than half-fixed.

### Fixtures and test repairs that came with it

The task set grew by five shapes a daily agentic user really hands over: `cross-file-refactor`

### E · The HARDENED provider is implemented; activation needs the owner

`apps/cli/src/provider/` is a real provider, not an interface:

- **boundary.ts** measures the boundary (account, elevation, store writers via an
  `icacls` decision that cannot mistake a read ACE for a write grant, service and
  its account, and what a restricted runner could actually be jailed with).
  Nothing is created: the privileged steps are the owner's.

### First one diagnosed, precisely (`pre10-env-authority`)

The probe asserts that every executed file lies inside Amabie's own trusted set,
and it builds that set by **hardcoding a mirror** of `trustedDirs()` from
`apps/cli/src/onboarding.ts` (`pre10-env-authority.mjs:27-35`). The product's
`gitExe()` resolves git from fixed literal candidates — which is deliberate, so a
PATH shim can never become git — and on this host that is
`C:\Program Files\Git\cmd\git.exe`, a directory **outside** the mirrored set. So
the promotion step's `exec.file` is reported as untrusted.

Two things are wrong, and they are fixable in this order:

1. **The mirror should not exist.** `trustedDirs()` is not exported, so the probe
   copies it; any future change to the product's trust set silently desynchronises
   the assertion that is supposed to police it. Export the set (or a
   `trustedDirsFor(platform)` helper) and have the probe import it, so there is one
   source of truth.
2. **The set is incomplete for what Amabie actually executes.** `gitExe()`'s
   literal candidates should be part of the trusted set by construction — the
   directories it will execute git from are, by definition, directories Amabie
   trusts. Add them at the same place the candidates are defined rather than as a
   second list.

Neither change should widen program resolution: the fix is to make the *declared*
trust set match the set of directories Amabie executes from, then have the probe
read that declaration instead of paraphrasing it.

**Fixed in `1abe0b2`.** The git candidates became a named helper whose
directories are part of the (now exported) `trustedDirs()`, and the probe imports
that declaration rather than mirroring it. `pre10-env-authority` reports ALL PASS,
including its honest controls — which is the check that the fix did not simply
delete the assertion.

### Third and fourth: `m8-promotion` is the SAME root cause, and it is now identified

Running `m8-promotion` with full output shows both its failures, and they are one
defect — the same precedence defect as `m9-authority`:

1. *"mid-plan commit attack: candidate HEAD moved during verification → REFUSED
   (sandwich), honest recovery on re-run"* expects the output to say
   `/changed during verification/`, but the run reports **`CANDIDATE FAIL — 1/1
   step(s) not green; the trusted base was not touched.`**
2. *"cross-case hygiene: … attempted repos land exactly once"* expects one
   promotion bundle and finds zero — a second-order effect of (1), because the
   repo never reaches the promote path.

**The defect**: when the sealed plan fails, verification returns the plan's verdict
before the identity/authority sandwich is reported, so a change witnessed *inside
the verification window* is presented as "your tests failed" instead of "your
candidate moved underneath me". That is not a security hole — a plan failure blocks
promotion anyway — but it is a **reporting** failure with real cost: it sends an
agent to fix tests when the actual event is an integrity violation, and it hides
the tamper from the human reading the evidence. The doctrine already requires the
opposite for the passing case (`m9-authority` forces BLOCKED on drift); the failing
case must be symmetric.

**The fix is one precedence change** in the verification path of
`apps/cli/src/candidate.ts`: evaluate the post-window identity/authority checks
before finalizing the plan's outcome, so a witnessed mid-window change (or
authority drift) yields its own refusal and message regardless of whether the steps
passed. It touches no gate's strength — every guard already fires; the question is
only which one gets to speak.

So of the six reds: **one fixed, two explained by a single identified defect, three
undiagnosed** (`pre10-acceptance`, `master-pass-mutations`, `f3-acceptance-growth`
— the last two cascade: `master-pass-mutations` aborts because the `pre10`
baseline arm is red).

**Attempted, and it is NOT a simple precedence move** (experiment reverted; the
tree is green at `fd08b48`). Moving the sandwich ahead of the plan's verdict was
implemented two ways and re-run:

- *First attempt* — compare HEAD/tree before and after the window: the probe still
  reported `CANDIDATE FAIL`, because this attack makes the candidate **dirty**
  inside the window rather than moving its HEAD.
- *Second attempt* — also treat "was clean, is now dirty" as a mid-window change:
  the refusal then fires and the message assertion **passes**, but the probe's next
  step fails: *"re-promote of the stable head failed: expected 0, actual 2"*. The
  refusal left state that the honest recovery re-promote trips over — most likely
  the refusal artifact itself (an authority/refusal event) being read by the next
  run as a reason to refuse again.

So the real defect is two-part: the sandwich must speak before the plan's verdict,
**and** its refusal must leave the candidate recoverable by re-running after the
worker commits (only *authority* tampering earns a quarantine; a candidate that
moved under the verifier does not). That is exactly the kind of change that must be
made with the whole `candidate.ts` verify/refuse/quarantine path in view and proven
by re-running `m8-promotion` *and* `m9-authority` — not by iterating against one
assertion at a time, which is what the two attempts here demonstrate.

**Where to look first, and why.** The M9 sandwich takes a *pre-window* fingerprint
(`candidate.ts:505`, "fingerprint the authority bytes AND the evidence tree") and
compares it after the run. An early return inserted before that post-window
comparison **closes nothing** — if the window's state (the fingerprints, or a
"window open" marker) is only retired by the post-window check, then every early
refusal leaves it behind, and the NEXT invocation reads the stale window as reason
to refuse. That is the most likely mechanism behind the observed "re-promote of the
stable head failed: expected 0, actual 2", and it explains why the message
assertion passed while the recovery assertion broke. So: before touching the
precedence again, establish whether the post-window authority comparison performs
bookkeeping that every refusal path must also perform (or must be made idempotent /
re-entrant). If it does, the fix is to close the window on **every** exit from
`verifyCandidate` — a `finally`-shaped change — rather than to reorder the verdicts.

**That hypothesis is REFUTED** (checked in `candidate.ts`, not guessed): the
pre-window snapshot is a plain in-memory value (`const preAuth =
snapshotAuthority(authority)`, line 516), the post-window comparison is
`authorityDrift(preAuth, authority)` plus the seal re-check, and the ONLY persistent
side effect is `stampQuarantine` inside `authorityBlock` (line 376), which runs
solely when a *during/after* catch is actually found. An early `blocked(...)` return
therefore leaves no window state behind, and no quarantine.

So the recovery failure has a different cause, and the next thing to read is the
probe's own recovery sequence (`m8-promotion.mjs`, the `midplan` scenario) rather
than more of `candidate.ts`: the question is whether the scenario's step moves the
candidate on *every* run — in which case an inserted check correctly refuses again
on the recovery run while the probe expects that run to be judged on its own
merits — or whether the probe cleans the candidate and a fresh run should proceed.
The answer decides whether the fix belongs in the precedence at all, or in what the
probe's recovery is entitled to expect.

**Answered: the probe's expectation is coherent, and the fault is in our refusal.**
`m8-promotion.mjs:260-283` builds a candidate whose sealed test step, *if*
`marker.txt` contains `FAIL`, rewrites it to `ok` and commits inside the window —
once. The scenario asserts exactly two things: run 1 is refused with
`/changed during verification/`, and run 2 (`isolate --promote`) **succeeds** on the
same committed state, because the step's guard means it does not commit again. That
is a correct, honest recovery contract: the tamper is named once, and the worker's
own commit is then promotable. So the fix does belong in the refusal — it must
report the sandwich **and** leave the candidate exactly as promotable as it was.
An early `blocked(...)` return evidently changes something run 2 depends on; find
out what by reading run 2's own output (see the method note below) rather than by
reordering the verdicts again.

**Method note: the diagnostic was hidden by filtering.** The probe prints
`r2.stdout` inside its own failure message, and the runs in this record filtered
output through a pattern list (`FAIL|expected|actual|…`) that cut that block — which
is why "expected 0, actual 2" arrived without the reason run 2 refused. Run the
probe and read the **whole** failure block before changing anything; the answer is
very likely already in it.

**And it was. Reading the unfiltered block overturns the framing above.** The
midplan step does not fail because a verdict masked a tamper — it fails because the
**child process cannot load a module**:

```
✗ tests: npm run test (exit 1)
  … at Object..js (node:internal/modules/cjs/loader:2074:10)
  … at Module.load (node:internal/modules/cjs/loader:1656:32)
  status: 1, signal: null, output: [ null, null, null ]
```

So run 1 reports `CANDIDATE FAIL` because the scenario's own command did not run to
completion in that candidate, and the sandwich never gets the chance to speak. The
likely cause is the **fixture** — the mid-plan step script as loaded by Node 26 on
this host — not the refusal precedence. (With the sandwich moved earlier, run 1's
message assertion did pass, which means the plan had run far enough to move the
candidate in that attempt; the two observations are consistent only if the module
error is intermittent or state-dependent, which is itself worth knowing.)

What to do next, in order: reproduce the fixture's command directly inside the
`midplan` temp repo the probe leaves behind and read its stderr; if it is a
fixture/toolchain artefact, fix the fixture and re-run — the product may need no
change here at all. **The earlier "reporting precedence" framing in this section is
superseded for `m8-promotion`**: it was inferred from truncated output. The
`m9-authority` label observation (`fail` where the mandate is `blocked`) came from a
different assertion and has not yet been re-examined in this light.

### Fixed during v1.1

`probe: architecture-metrics` asserted that `amabie status` performs zero writes,
and it was right to: the sealed-copy level report called the *writing* probe, so a
command documented as zero-write made three write syscalls (invisible on disk,
because the probe file is created and unlinked). `status`, `result` and `agents`
now use a read-only level assessment; the writing measurement stays where writing
is already part of the job.

## Delivered

- **Projects**: Python, Rust and Go adapters behind the one `ProjectAdapter`
  contract, with discovery that never invents a check (a tool named in a comment
  or a description is prose), deterministic polyglot composition at a repository
  root, and toolchains **pinned to absolute paths at setup** so PATH is never
  consulted during verification.
- **Agents**: an honest capability table (`GATED` vs `ADVISORY`) surfaced by
  `amabie agents`; `amabie agents install codex` writes a marked, removable
  `AGENTS.md` block; `AGENTS.md` gives every harness the repository rules.
- **Machine interface**: `amabie result --json` plus a global `--json` where
  stdout is exactly one versioned envelope, prose moves to stderr, and exit codes
  and status words are identical with and without the flag.
- **Workflow**: `amabie work` / `amabie finish` orchestrate the existing
  primitives (register + isolate; verify + promote) without re-implementing a
  gate, and never close a subjective duty.
- **Adaptive fast path**: a project may declare which paths each check depends on
  (`amabie.paths`); setup **validates and seals** that declaration with the plan,
  and `doctor --fast` (opt-in) leaves out only the checks whose declared paths the
  change provably missed — printing every skip with its reason and carrying them
  in the JSON envelope as `skipped`. Undeclared checks always run, an empty change
  set runs everything, and `finish`/promotion never take the flag.
- **Cost**: model-neutral metrics (off by default, fail-open, no free text or
  paths recorded).
- **Trust**: the Astra P0 kernel merged in — lossless authority signing, a
  compare-and-set sealed store, the authorization kernel, and the platform
  contracts — with the mutation probe as its behavioural specification.
- **Adoption**: `CONTRIBUTING.md`, `AGENTS.md`, `CHANGELOG.md`, root
  `SECURITY.md`, issue/PR templates, Dependabot, `.editorconfig`, a machine-
  readable `schemas/spec.schema.json`, a CI restructure (the proof job is no
  longer skipped behind a red matrix) and a tag-driven release workflow.

## Deliberately NOT delivered

**1. The provider chain — so `HARDENED` does not exist.** No installed broker
service, authenticated IPC, immutable source import, sandbox, supervisor, review
path, promoter or enforced network policy. The contracts exist; nothing implements
them. The CLI's real paths still run on the LOCAL sealed store, and the same uid
can replace the store, its keypair and its ledger together. See
[`TRUST-ARCHITECTURE.md`](../TRUST-ARCHITECTURE.md).

**2. Fast-path drift reporting — CLOSED** (`f7d8673`). A live edit to
`amabie.paths` is now compared against the seal and reported as drift, and drifted
authority makes `doctor` refuse *before executing anything*, so a widened
declaration grants neither a skip nor a run. Kept here as a record rather than a
gap.

**3. Runner-observation adapters — PARTIALLY CLOSED (the interface, not the
channels).** `runners.ts` now states per runner whether a strong label is
reachable and why not, so the gap is explicit and unknown runners are
`INCONCLUSIVE` by construction. What has NOT changed: only mocha has a real
injected-observer channel, and the pin table still covers exactly one npm release
(mocha 10.8.2). jest, vitest, ava, `node --test`, pytest, `unittest`, cargo and go
remain `INCONCLUSIVE_ONLY`. **cargo and go were never executed** — neither
toolchain is installed on this host — so their adapters are registered designs,
not demonstrated paths, and are labelled as such. Adding a runner still means
adding an injected observer, a pin **and** its reviewed manifest.

> **SUPERSEDED by Update 2 (kept as the record).** This paragraph is wrong today on both
> counts: `node --test`, pytest and `unittest` now HAVE injected observers with pins
> (`runner-observation-node-test.mjs` 7/7, `runner-observation-pytest.mjs` 7/7, each also
> wired through the round path), the STRONG set is no longer `{mocha}`, and the Go and Rust
> toolchains WERE provisioned workspace-locally and executed through `setup` + `doctor`
> (`go-project-e2e.mjs`, `rust-project-e2e.mjs`). What survives unchanged is the part that
> matters for honesty: **cargo and go still have no per-test observation channel** — libtest
> refuses `--format json` on stable and `go test -json` events are forgeable by subject code —
> so those two remain `INCONCLUSIVE_ONLY` for the stated reasons, not because the toolchain is
> missing.

**4. Nested ecosystem scopes — CLOSED.** `amabie.scopes.json` declares
`{ path, ecosystem }` scopes. Declared ⇒ exactly those scopes; undeclared ⇒ root
only, so an `archive/` or `examples/` directory still cannot silently add checks.
An unusable declaration stops setup in full rather than shipping a partial plan.
Two real defects were found and fixed while closing this, both by the feature
smoke: a scoped step used the repository's flat package manager (so a nested
`web/` Node step rendered as `python run test`), and it ran with `cwd` at the
repository root (so `npm` could not find `web/package.json`). `PlanStep` now
carries its own scope's `pm`, sealed with the step.

**5. Node-free distribution — CLOSED for the host target.** `tooling/standalone.mjs`
builds a single executable with Node embedded via `node --build-sea` and executes
it with Node removed from `PATH` before reporting success. `amabie-win32-x64.exe`
is built and proven here. **Linux and macOS artifacts are NOT built and NOT
claimed**: `--build-sea` embeds the running `node` binary, so each target must be
built and executed on its own host. There is still no published `npm install
amabie`.

**6. An MCP server — CLOSED.** `amabie mcp` serves six tools over stdio. It is a
transport with no authority of its own: every call runs the same CLI and relays
its verdict and exit code unchanged, no tool can take an argument that influences
a verdict, and `amabie accept` is deliberately not exposed.
