## GAP A — EVERYDAY TOKEN EFFICIENCY

**CURRENT STATE.** The everyday path is measured at **379,792** model tokens
against plain **409,824** — **92.7 %**, a **7.3 %** saving at equal measured
correctness (`CHANGELOG.md` 1.3.0 section). This is not uniform: per cell it is
**82.9 %** (`bound-requirements` 126,977 → 105,255), **100.02 %** (`bug-sum`
70,070 → 70,083) and **96.1 %** (`stateful-replay` 212,777 → 204,454). The
v1.4 target is **≤ 75 % of plain in aggregate**.

**USER IMPACT.** A user evaluating Amabie on cost sees a real but small saving,
and one measured task is very slightly *more* expensive. The published claim is
therefore narrow, and it is narrower than the "up to 87 %" figure that appears in
the confined experiments — which is why that figure ships with an adjacent
qualification and an authored-arm caveat.

**ROOT CAUSE (measured, not hypothesised).** The token cost of the everyday path
is **entirely the agent's own context**: `cmdCheckpoint`
(`apps/cli/src/onboarding.ts:2952`) makes **no model call of any kind**. The only
model-spawning code in the repository is `apps/cli/src/provider/model-transport.ts`
(the OS-confinement provider on the *candidate* path, a different subsystem).
So Amabie cannot "spend fewer tokens" directly; it can only change how much the
agent must read. That is already bounded in every cheap way:
- the hook's block reason is capped at **1200 chars**
  (`apps/cli/src/failure-payload.ts:40 MAX_TOTAL_CHARS`),
- the silent allow is **0 bytes** (`onboarding.ts:3127`),
- full runner output goes to disk and only its **path** is printed,
- the sealed plan runs twice (working tree at `:3005-3010`; discrimination base
  at `:1610-1618` via a throwaway `git worktree`) but **nothing from either run
  reaches the model**.

**MEASUREMENT.** Two independent routes to a lower number have already been
measured and both are bounded, in this repository's own recorded work:

| Route | Measured ceiling | Source |
|---|---|---|
| Remove the MCP standing payload | ≈ **2 points** | `docs/V1.3-PRODUCT-AUDIT.md:437-453` |
| Eliminate the repair turn entirely | ≈ **5.9 %**, "an upper bound on an impossible act" | `docs/V1.3-PRODUCT-AUDIT.md:483-499` |

The audit's own conclusion: "**92.7 % → ~85 %**, not 75 %" (`:501-505`).

**THE OPEN FINDING THAT MATTERS MOST.** The 92.7 % figure **excludes** a standing
cost that is paid on every turn of every session: `amabie setup` registers the
MCP server, and the MCP instructions plus six tool definitions are **5,726 B per
turn**, of which **1,923 B (33.6 %)** is **expert-only ceremony**
(`amabie_work` 1,139 B + `amabie_finish` 784 B) that an everyday user never
invokes. `docs/V1.3-PRODUCT-AUDIT.md:455-459` records this as an OPEN finding and
states plainly that "the real everyday footprint is somewhat worse than the
measured ratio". **That is an honesty defect in the published claim, and it is
the single highest-leverage token item in this release.**

**PROPOSED SMALLEST FIX.** Do not touch the gate. Two changes, both provably
safe:
1. **State the footprint honestly**: extend the token claim to include the
   standing per-turn payload the measurement excluded, so the published ratio
   matches what a user actually pays.
2. **Stop advertising expert tools to everyday users**: the everyday
   configuration needs `result`/`doctor`/`status`; `work`/`finish` are the
   measured-more-expensive expert path (177.8 %). Measure the standing payload
   before and after with the existing `tooling/probes/v13-standing-context.mjs`.

**SECURITY RISK.** Low for (1) — text only. Low-but-real for (2): removing a tool
from the *advertised* set must not remove it from the *expert* surface, and must
not change any verdict, exit code or gate. The MCP server must keep exposing the
same authority to a caller that asks for it; only the standing advertisement
changes.

**EXPECTED COMPLEXITY.** Small. Both are bounded edits plus one deterministic
probe re-run. No new architecture, no new state.

**SUCCESS CRITERION.** The standing per-turn payload is measured **lower**, the
expert surface still exposes the same tools on demand, every verdict/exit code is
byte-identical, and the published token claim is either updated to the measured
aggregate footprint or explicitly annotated with what it excludes.
**The ≤ 75 % target is NOT a success criterion for this gap** — see the verdict.

**VERDICT (this release).** **REJECTED WITH EVIDENCE — the target is not
reachable without trading the gate for the number.** Both available routes are
measured at ≈ 2 points and ≤ 5.9 % respectively and are mutually exclusive, and
their impossible sum lands at ≈ 85 %. Reaching 75 % would require removing
verification work, which the priority order forbids. What this release DOES do is
close the honesty defect (the excluded standing payload) and take the safe part
of the win. See §TOKEN RESULT of the final audit.

## GAP B — CURSOR

**CURRENT STATE.** Cursor is detected and reported as **UNMEASURED**
(`apps/cli/src/agents.ts:86-92`, `gating: false, gatingMeasured: false`). The
capability table says exactly what is and is not known: Cursor documents importing
Claude Code hooks (including `Stop`), which *would* make the hook Amabie already
installs a completion gate, but this project has never reproduced that on a real
Cursor install; and Cursor documents no way to remove its native tools, so
Amabie cannot confine Cursor's own edits.

**USER IMPACT.** A Cursor user gets an honest "we have not verified this" instead
of a false promise, but also gets no verified protection.

**ROOT CAUSE.** Absent environment, not absent capability.

**MEASUREMENT (this release).** Probed the host directly: `cursor-agent` is **not
on PATH**; `cursor` is **not on PATH**; and none of
`%LOCALAPPDATA%\Programs\cursor`, `%LOCALAPPDATA%\Programs\Cursor`,
`%APPDATA%\Cursor`, `%USERPROFILE%\.cursor` exists. **No real Cursor host is
available on this machine.** A result cannot be produced from here, and the
mandate forbids faking one.

**PROPOSED SMALLEST FIX.** None that can be executed here. The smallest honest
change is to keep the UNMEASURED report and mark the gap **EXTERNAL TESTING
REQUIRED** with a precise procedure for whoever has a Cursor host: install
`amabie setup`, confirm the imported `Stop` hook fires, and test the two cases
(valid change → allowed; undiscriminated completion → blocked), recording whether
Cursor synthesises `stop_hook_active` and `cwd` for imported hooks.

**SECURITY RISK.** The dangerous "fix" would be to *claim* gating on the strength
of the vendor's documentation. That is precisely the overclaim this project
exists to prevent, and it is refused.

**EXPECTED COMPLEXITY.** Blocked, not large: the work is waiting on a host.

**SUCCESS CRITERION.** Two recorded hook invocations on a real Cursor install —
one allowed, one blocked — with the raw inputs and outputs. Until then the answer
stays UNMEASURED.

**VERDICT.** **EXTERNAL TEST REQUIRED.** Explicitly permitted by the mandate
("If no suitable Cursor environment is available: do NOT fake the result") and
explicitly not allowed to block the release ("Do not make the whole v1.4 release
wait forever on unavailable external infrastructure").

## GAP C — SECOND REAL AGENT INTEGRATION

**CURRENT STATE.** Only Claude Code is a **gating** integration
(`agents.ts:56-64`, `gating: true`). Codex is advisory only, and the capability
table states the reason as: *"no completion hook exists to gate"*
(`agents.ts:71`). Cursor is unmeasured. The claim that Amabie is "a safety engine
with thin agent adapters" is therefore **asserted but not demonstrated**: one
adapter is one data point, and it is the one this project was built around.

**USER IMPACT.** A developer who does not use Claude Code cannot get a gated
completion. The architecture claim is unproven to exactly the audience that needs
it.

**ROOT CAUSE — AND THE CAPABILITY TABLE IS NOW WRONG.** Measured on this host:
`codex --version` → **`codex-cli 0.154.0`**; `codex features list` reports
**`hooks  stable  true`** — enabled. `--help` exposes
`--dangerously-bypass-hook-trust`, and `~/.codex/config.toml` carries a
`[hooks.state]` table with persisted `trusted_hash` entries at
`…\.codex\hooks.json:<event>:…`. The vendor's hook reference
([learn.chatgpt.com/docs/hooks](https://learn.chatgpt.com/docs/hooks.md))
documents a **`Stop`** event whose contract is, verbatim:

> `Stop` expects JSON on `stdout` when it exits `0`. … To keep Codex going,
> return: `{ "decision": "block", "reason": "Run one more pass over the failing
> tests." }` … For this event, `decision: "block"` doesn't reject the turn.
> Instead, it tells Codex to continue and automatically creates a new
> continuation prompt that acts as a new user prompt, using your `reason` as that
> prompt text.

with `stop_hook_active` ("Whether this turn was already continued by `Stop`") —
**the same contract, the same loop guard, and the same JSON shape Claude Code
uses**. Hooks are discovered at `<repo>/.codex/hooks.json`, and non-managed hooks
require a one-time review/trust recorded against the hook's hash.

So `agents.ts:71`'s "no completion hook exists to gate" is **stale and false as
of Codex CLI 0.154.0**, and Codex is a real second adapter rather than a wish.

**MEASUREMENT.** Host probe above. The end-to-end measurement to be produced by
this release: a `<repo>/.codex/hooks.json` `Stop` hook that runs
`node "<cli>" checkpoint`; then two recorded invocations of the hook exactly as
Codex drives it (one where the sealed plan passes → silent allow, one where it
fails → `{"decision":"block",…}`), plus a real `codex exec` run if the harness
cooperates on this host.

**PROPOSED SMALLEST FIX.** Add a **gating** Codex adapter that *reuses the
existing checkpoint implementation* (one implementation, no fork — the same rule
the file's header already states for Claude Code): a `.codex/hooks.json` writer
with the same containment discipline as `installStopHook`, installed by
`amabie setup` when Codex is the detected harness, removable by
`amabie agents uninstall codex`. Update the capability table to say what was
measured, and keep reporting the one-time hook-trust review honestly (it is real
friction: an untrusted hook does not run).

**SECURITY RISK.** **Medium, and it is the main risk of this release.** A new
writable file (`.codex/hooks.json`) inside the user's repository; a hook that
executes a command; and a vendor-specific trust mechanism Amabie does not own.
Mitigations that must hold: the same link/containment checks as every other
Amabie write, ownership recorded in `.amabie` so `uninstall` removes exactly
Amabie's entries, no new authority for the hook (it runs the same `checkpoint`
that already exists and can only *report*), and **no claim of gating until an
invocation has been observed**.

**EXPECTED COMPLEXITY.** Moderate. One writer + one removal path + capability
table + tests + a probe. No change to the verification core.

**SUCCESS CRITERION.** Amabie writes a Codex `Stop` hook; a recorded invocation
blocks a completion whose sealed plan fails and allows one that passes; the
capability table reports Codex as gating **only** because that was observed; and
`amabie uninstall` removes Amabie's entries and nothing else.

**VERDICT (this release).** **SOLVED — and MEASURED end to end.** A real `codex exec` session
(`codex-cli 0.154.0`) executed Amabie's `Stop` hook **twice**: once blocking
(`{"decision":"block","reason":…}` on stdout, exit 0) and once with `stop_hook_active: true`
allowing — and the harness **actually continued the turn** on the reason Amabie supplied. Because
that invocation was observed, `apps/cli/src/agents.ts` now reports `gating: true` for Codex with
`gatingMeasured: true`; the probe is `tooling/probes/v14-codex-stop-hook.mjs` (15/15 observations,
exit 0), and it is registered as a SKIP-aware step in `verify:productization`. Two measured facts
that must travel with this claim: **Codex has two independent trust layers** (a project `.codex/`
layer that is not loaded at all until the *project* is trusted, and a per-hook record that
`--dangerously-bypass-hook-trust` can skip), and **Codex rejects an entire `hooks.json` that carries
an unknown top-level field**, so Amabie's writer emits only `hooks` and preserves everything else.
Until the one-time trust review is done the hook is written and **gates nothing**, which the
capability table states on the row itself rather than leaving to the documentation.

## GAP D — PROJECTS WITH LITTLE EXISTING EVIDENCE

**CURRENT STATE.** Discovery is broader than the refusal messages suggest. Node
accepts exactly `typecheck, type-check, test, build, bench, benchmark, e2e,
test:e2e` (`apps/cli/src/project.ts:50-53`). A **universal** adapter
(`apps/cli/src/universal.ts`) discovers Makefile targets, Taskfile/Justfile,
shipped `gradlew`/`mvnw` wrappers, configured CMake/Meson/Zig/Swift/Elixir/
Crystal/Rake/Composer/PHPUnit, and **CI `run:` lines**
(`universal.ts:332-352, 404-565`). Python/Rust/Go have real manifest adapters
(`apps/cli/src/ecosystems.ts:120-248`).

**USER IMPACT.** Three concrete, reproducible failures on the poorly-structured
repositories this gap is about:
- **D1 — the actionable line is thrown away.** When the universal adapter finds
  an *ambiguity* it deliberately returns **zero checks plus one clarification
  line** (`universal.ts:539-559`). But `setup` refuses for "no recognised check"
  at `onboarding.ts:2302` — *before* the loop that would print
  `composed.empty` (`:2306`). The user gets a generic wall of text and loses the
  single line that says what to do.
- **D2 — the refusal text understates Amabie.** Both no-check refusals
  (`:2270`, `:2302`) list only Node/Python/Rust/Go. A Makefile-only, CI-only,
  Taskfile-only or Gradle-wrapper repository *is* supported, and is told it is
  not.
- **D3 — a real declaration that exists is not read.** A Node repository whose
  CI runs the check but whose `package.json` does not declare it discovers
  **nothing**: CI lines naming `npm`/`node` are skipped when a native manifest is
  present (`universal.ts:521-522` + `nativeAdapterOwns` `:270-282`). Likewise a
  Python repo whose only declaration is `mypy.ini` yields Python with an **empty
  plan** and is refused, because `mypy.ini`/`ruff.toml` count only as *presence*
  and their contents are never read (`ecosystems.ts:120-121` vs the source list
  at `:133-137`).

**ROOT CAUSE.** Not missing discovery — **missing disclosure**. The engine knows
more than it tells the user, and in D1 it discards the one sentence that would
have resolved the situation.

**MEASUREMENT.**
- `apps/cli/src/onboarding.ts:2302` returns before `:2306`.
- `universal.ts:554` is the ambiguity path; `:521-522` is the npm/node skip;
  `ecosystems.ts:133-137` is the content-read source list that omits
  `mypy.ini`/`ruff.toml`.
- Existing coverage: `apps/cli/test/universal-project.test.ts:123-313` covers
  Makefile, CMake, CI `run:` lines, "invents NOTHING when the repository anchors
  nothing" (`:181-189`) and the **one-line ambiguity** (`:191-209`) — but only at
  the adapter level. **Not covered:** a full `amabie setup` end-to-end on a
  Makefile-only / CI-only / Taskfile-only repository, and a `mypy.ini`-only
  Python repository.

**PROPOSED SMALLEST FIX.** Text and ordering only — **no new discovery**:
1. Print the universal adapter's clarification line on the refusal path instead
   of dropping it (move/duplicate the `composed.empty` disclosure before the
   `:2302` return).
2. Rewrite both refusals to name what Amabie really reads, including the
   universal contract, so the message stops understating the product.
3. Add an end-to-end `setup` test on a Makefile-only fixture and on a
   `mypy.ini`-only fixture, pinning whatever the honest answer is.

**SECURITY RISK.** **Low, and the boundary must be stated explicitly.** This gap
is exactly where "make onboarding easier" can become "let the worker invent
authority". The line that must not move is already enforced and documented:
binding is authored by the project in `package.json` `amabie.proofs` (or
`amabie.project.json` `proofs`), every key must be a full 64-hex digest and every
value must name a script **already in the plan**, or the seal **throws**
(`project.ts:258-261`); the checkpoint refuses to certify before executing when
authority drifted (`onboarding.ts:2985-2992`); and `work` refuses with
**`REQUIREMENT UNBOUND`** — no worker, no candidate — when a declared requirement
has no sealed check (`orchestrate.ts:101-109`,
`provider/model-transport.ts:27`). **CHECK DISCOVERY may get better; SEMANTIC
AUTHORITY must not move at all.** Deriving a check from a project's own contract
(a `tsconfig.json`, a declared `mypy.ini`) is discovery and is allowed; deriving
*proof* for a requirement is not, and stays the operator's act.

**EXPECTED COMPLEXITY.** Small. Text, ordering, and two fixtures.

**SUCCESS CRITERION.** On a Makefile-only repository, `setup` either succeeds
using the discovered target or refuses **naming the universal contract and the
ambiguity line**; on a `mypy.ini`-only repository the refusal is accurate about
what was found; and no path exists by which discovery creates a binding. Both
pinned by an end-to-end test.

## GAP E — BEGINNER UX

**CURRENT STATE.** The everyday promise is "install → `setup` once → use the
agent normally", and the mechanism delivers that (`setup` installs a `Stop` hook;
`checkpoint` speaks at the end). But the *language* does not hold the line: the
everyday surface leaks internal vocabulary that the mandate says the ordinary
user must not need.

**USER IMPACT — the concrete leaks, quoted.**
- `setup`, on a path any user can hit: *"authority could not be sealed in the
  trust store (…) — Amabie will not finish wiring a project whose sealed copy it
  cannot mint"* (`onboarding.ts:2391`), with the next step naming
  `AMABIE_TRUST_STORE`.
- `setup`, whenever a registered requirement is unbound (`:2474-2477`): *"N
  registered requirement(s) have NO sealed proof"*, `unbound: <64-hex digest>`,
  *"sealed plan script(s) available to bind"*.
- `setup` on a seal failure: **`REFUSED — ` + a raw internal throw**, reachable
  text *"package.json amabie.proofs must map full task/requirement digests to
  recognized plan scripts"* (`:2294` ← `project.ts:260`).
- `doctor`: *"a proof obligation is objectively violated"* (`:2852`), *"N
  objective obligation(s) have no adequate proof"*, `UNPROVEN
  [per-requirement] (objective)` (`:2877-2884`), *"(NO PROOF, NO DONE)"*
  (`:2891`).
- `result`: *"no sealed checks, no proof, no result"* (`:3449`).
- `main.ts:436-438` prints a **raw exception message** for any uncaught error on
  **any** command, everyday ones included.

**ROOT CAUSE.** Everyday and expert output were written as one surface. The
vocabulary is *correct* — it is just the wrong register for the audience, and in
the `REFUSED — <throw>` case it is not even a sentence.

**MEASUREMENT.** Every citation above is a literal string read from the source at
the line given. The every-path/expert-path split is real and already encoded:
`work`/`finish`/`bind`/`task`/`isolate`/`accept` are the expert surface
(`orchestrate.ts`, `candidate.ts`) and are *allowed* this vocabulary; the eight
strings above are on `setup`/`doctor`/`result`, which are not.

**PROPOSED SMALLEST FIX.** Translation, not simplification, and no loss of
meaning: every everyday message keeps its exact semantics and its exact exit
code, and the internal detail moves behind `--verbose` (which already exists and
already gates detail output — `onboarding.ts:2165-2175`). Two rules: **no
undifferentiated vocabulary on `setup`/`doctor`/`result`**, and **no raw
exception interpolation in a user-facing verdict**. Where a decision is genuinely
needed, say so in one sentence, in the shape the mandate specifies.

**SECURITY RISK.** **Low, with one trap.** Dumbing down must never become
vagueness: a refusal must still say what was refused and why, and must still exit
the same non-zero code. "Amabie could not verify this change" is acceptable;
"I could not do that" is not, because it removes the information a human needs to
act. Security semantics are **translated, not weakened**.

**EXPECTED COMPLEXITY.** Small — bounded text edits plus tests that pin the new
strings and the unchanged exit codes.

**SUCCESS CRITERION.** A user who has never read the architecture can complete
install → `setup` → a verified completion and, on each of the eight paths above,
is told in plain language what happened and what to do, with the internal terms
still available under `--verbose` and **every exit code unchanged**.

## GAP F — COMMUNITY READINESS

**CURRENT STATE.** `README.md` leads with the everyday path, carries the
corrected exact token claim with the withdrawn "never worse" phrasing removed,
states the authored-arm caveat and the confined-coverage limitation, and names
`v1.3.0`. `docs/RELEASE-1.3.md` and `docs/V1.3-RELEASE-AUDIT.md` exist. There is
no consolidated troubleshooting page, no issue template capturing diagnostics,
and — a real gap for this section — the **local observability** the testing phase
needs is not assembled in one place (§18 of the mandate).

**USER IMPACT.** An evaluator can read what Amabie claims, but cannot easily
(a) reproduce a demo, (b) report a problem usefully, or (c) collect the
diagnostics that would make their report actionable.

**ROOT CAUSE.** Release documentation was written for a release; the incoming
phase needs documentation for *arrival*.

**MEASUREMENT.** Not a defect measurement — an inventory. Present: README
everyday path, benchmark methodology, security model, known limitations,
`CONTRIBUTING.md`, `docs/COMPATIBILITY.md`, `examples/README.md`. Missing:
troubleshooting, issue template, a stated supported-agent table on the README
surface, and a single documented way to export a run's diagnostics.

**PROPOSED SMALLEST FIX.** Documentation and templates only, and **nothing
manufactured**: a 2-minute quickstart that takes a reader from install to one
blocked and one allowed completion; a troubleshooting section for the failures
actually observed (no harness, no checks declared, checks fail, `NOT PROVEN`);
an issue template asking for `amabie --version`, `amabie status --json`,
`amabie doctor --json` and the platform; and a local diagnostics export. **No
testimonials, no adoption claims, no fake community** — the mandate forbids it
and this project's doctrine makes it self-defeating.

**SECURITY RISK.** Minimal. The one risk is a template that invites pasting
logs: the template must ask for the **JSON envelopes**, which name paths to
evidence rather than embedding it, exactly as the advisory block already
instructs agents (`agents.ts:118-124`).

**EXPECTED COMPLEXITY.** Small.

**SUCCESS CRITERION.** A new user can go install → first blocked completion →
first allowed completion using only the quickstart; can report a problem with a
template that yields a diagnosis without a round-trip; and nothing on the page is
a claim that was not measured.

release commit (`540393a`), run **35513360741**, and each failure is now
classified. **Five distinct defects; four are fixed in this release, one is a
host limitation made explicit.**

**MEASUREMENT — the failing jobs and their real causes.**

|---|---|---|---|---|

| G2 | `core` ubuntu: `setup` exited 2 where the test expected 0 (`acceptance-scope`, `agents`, `discrimination-completion`) | Log text: `NEEDS ATTENTION — no supported AI harness detected`. `detectHarnesses` reads `<root>/.claude` **or the operator's `~/.claude`**; CI runners have neither, and the fixtures did not declare one | **TEST DEFECT** (host-dependent fixture) | **FIXED** |
| G3 | `confined-activation` failed **all five suites** (~50 red lines) off Windows | `apps/cli/test/confined-activation.test.ts:60` asserted `process.platform === 'win32'` in a top-level `before` hook | **TEST DEFECT** (fail-closed asserted as failure) | **FIXED** |
| G4 | `universal-project`: expected `gradlew test`, actual `./gradlew test` | `apps/cli/src/universal.ts:451` returns `./${w}` on POSIX and `w` on Windows — the **product is right** and the test hard-coded the Windows spelling | **TEST DEFECT** | **FIXED** |

A sixth instance of G2's class was found while fixing it and is being closed the
same way: probe fixtures such as `tooling/probes/v12-production-authority.mjs`
also run `amabie setup` in a temporary repository and depended on the operator's
home directory.

**USER IMPACT.** A contributor opening Amabie saw red jobs that were not about
their change, one of them with no explanation at all, and a cancelled job whose
status hid both the profile and the verdict. That is the "unexplained permanent
red" this gap names.

**ROOT CAUSE.** Fixtures and workflows encoded properties of the **developer's
machine** (a home directory with Claude Code; a Node new enough for
`--build-sea`) as if they were properties of the **product**. The product was
right in every case.

**PROPOSED SMALLEST FIX.** Exactly the five above: pin the standalone job to a
Node that has the flag (**26.3.0**, the version this workflow's `golden-proof`
job already runs); make the fixtures declare their own harness; give the
Windows-only suite an explicit `{ skip }` with its existing reason string
(a **SKIP is never a PASS**, and it remains visible in the counts); assert the
wrapper spelling the host actually uses; and give the Windows leg a budget that
covers its measured need so it **runs to completion** and reports a named verdict
instead of being cancelled.

**SECURITY RISK.** The risk here is the inverse of the usual one: making CI green
by **weakening a gate**. Every fix above is therefore either a *scheduling*
change, a *fixture* change, or a *message* change. **No assertion was deleted,
relaxed or skipped into a pass**, the fail-closed guards were kept (the
`confined-activation` `before` hook still asserts Windows if the skip is ever
removed), and `provider.test.ts`'s elevation assertions were made **stronger**
(they now cover the extra privileged Linux step `egress-policy`).

**EXPECTED COMPLEXITY.** Small, but it touches several files.

**SUCCESS CRITERION.** Every red job has a named, deterministic cause that a
contributor can read from the log; nothing is red for a reason that is about the
host rather than the change; and where a host limitation genuinely remains it is
**stated in the workflow itself, with its measured profile**, so the status is
explicit rather than mysterious.
