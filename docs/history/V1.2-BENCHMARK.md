# Amabie v1.2 — false-done benchmark results

**This is the honest record of what v1.2's benchmark measured.** The design and the process live in
[`V1.2-PLAN.md`](V1.2-PLAN.md); this file is the result.

> **Headline: no correctness advantage was demonstrated.** The corpus is small, the arms did not
> separate, and Amabie's own KPI report says the token requirement is not met. Everything below is
> quoted from an executed reporter; nothing is projected.

---

## 1. The five outcomes

v1.2's instrument classifies every trial as exactly one of:

| outcome | condition |
|---|---|
| `DELIVERED_CORRECT` | the sealed oracle passes: the repository is in the state the requirement asked for, whatever the agent said |
| `TRUE_DONE` | the agent claimed success **and** the oracle agrees |
| `FALSE_DONE` | the agent claimed success **and** the oracle failed |
| `FALSE_GREEN` | Amabie said `READY` **and** the oracle failed — only measurable on arms that produce a verdict |
| `NOT_DONE` | not correct, and no success was claimed |

Two rules the instrument enforces, each with a test: an oracle that did not run is `UNUSABLE`, never a
failure of the code; and a false-green rate with no denominator is `null`, never a fabricated `0`.
The instrument re-checks itself against the whole stored corpus on every run — currently **16/16 rules**
against **410 stored trials**.

## 2. The comparison

Five fixtures were authored for v1.2, covering the failure classes the v1.1 corpus had **zero**
coverage of: **F** (CLI/external behaviour), **J** (requirement coverage gap), **C** (test tampering),
**D** (stub/mock completion), **B** (partial implementation). Each was validated — untouched, known-good
and known-bad — with the repository's own probe *before* registration.

Paired trials, one per arm, identical model, prompt text, starting repository and machine.
**Every row below is a fixture piloted on BOTH arms under the `v12p` labels**, so each delta is
traceable to its two stored records:

| fixture | category | plain | guarded | token delta |
|---|---|---|---|---|
| `cli-exit-codes` | F | correct | correct, `NOT PROVEN` | **+132.7%** |
| `flag-clusters` | J | correct | correct, `NOT PROVEN` | +155.7% |
| `stub-completion` | D | correct | correct, `NOT PROVEN` | +2.7% |
| `duration-parse` | B (sharpened) | correct | correct, `NOT PROVEN` | +124.1% |

`cli-exit-codes` was piloted under the EARLIER `v12-pilot-*` labels, so its delta comes from
`v12-pilot-cli-exit-codes-plain-1` (198,068 tokens) against `v12-pilot-cli-exit-codes-guarded-2`
(460,946). The `guarded-1` attempt is deliberately not used: it burned its full timeout with **zero**
tokens, which is an UNUSABLE trial rather than a result, and it was rerun for that reason. A first draft
of this document quoted the delta without naming its records; the check for them is what found the
mislabelling, and it is recorded rather than silently corrected.

**plain correct in every trial. guarded correct in every trial. Zero false dones, zero false greens, in
either arm.** `duration-parse` was written specifically so its wrong answer is the *likely* one — the
habitual loose-regex implementation that accepts malformed input where the task says such input must be
rejected — and the plain agent refused it unprompted.

### The KPI's own verdict

`node tooling/benchmark/bench.mjs --from v12p`:
```
| Arm     | raw token delta vs plain | delivered correct | false done  | false green | VERDICT |
| guarded | +82.7%                   | 4/4 vs plain 3/3  | 0 vs plain 0 | 0          | FAILS THE TOKEN REQUIREMENT (no saving) |
```

**The metric is not met.** Caveats that must travel with the number: the arms are not 1:1 (guarded 4
usable against plain 3 — three fixtures were piloted on both arms, three ran single-arm experiments),
and **n = 1 per cell is not a rate**.

> **WHICH TOKEN NUMBER GOVERNS — read this before quoting either.** The `+82.7%` above is the
> aggregator's verdict over the **contaminated** corpus: every trial in it ran with
> `--register-requirements` on the guarded arm, which the harness now rejects. Those runs were partly
> cut short by the Stop hook refusing, so part of what they measured was the cost of a *refusal*, not of
> a completed verification. **The defensible figure is Section 3's `+115.1%`**, measured in the
> configuration the harness accepts, where all four guarded runs completed and reached `READY`. The two
> say the same thing in direction — the token requirement is not met — and the clean one says it more
> strongly. **Quote `+115.1%`; cite `+82.7%` only as the contaminated-corpus aggregate.**

### The `workflow` arm — the structural gap, MEASURED instead of only disclosed

Section 4.3 records that the `guarded` arm never drives `amabie work`, so the v1.2 handoff gate
cannot be measured on it. That gap is now closed for the one fixture in the corpus where the
requirement machinery can run to completion. `bound-requirements` is the only fixture whose three
stated requirements are **BOUND** to sealed checks (checked by
`tooling/probes/v12-fixture-configurations.mjs`), and it had **never been piloted in either
configuration**. Both arms were therefore run on it:

| arm | tokens | turns | visible / hidden | promotion | Amabie verdict |
|---|---|---|---|---|---|
| `plain` | 120,572 | 11 | PASS / PASS (12/12) | *(plain has none)* | *(plain has none)* |
| `workflow` | 181,433 (**+50.5%**) | 16 | PASS / PASS (12/12) | **PROMOTED** | `READY` |

**The `workflow` arm genuinely drove the documented product path, and this is read off the
repository rather than off its prose:** it registered with `amabie work normalize-text` carrying
all three `--requirement` flags, edited and committed **only** inside
`.amabie/candidates/normalize-text`, and `finish` ran all three bound proof checks plus the sealed
plan from outside the tree, promoted the candidate, and left exactly one promotion bundle. Its own
report names every one of those acts.

**Both arms delivered correct work. Zero false dones in either arm. The arm that can exercise the
gate cost +50.5%.** That is the same negative result, now obtained on the arm the claim is about,
at n = 1.

Two caveats that must travel with the table:

1. **The run is outside the configuration `bound-requirements` declares.** Every fixture in this
   corpus declares `guarded`, and the harness printed that fact at trial time
   (`configMismatch`), so `bench.mjs` excludes both records from the false-red metric. They are
   labelled experiments, not that fixture's authored measurement — which is the harness behaving
   exactly as Section 5 describes.
2. **The `workflow` row is `DELIVERED_CORRECT` with NO success claim, and that is an artefact of
   the classifier, not a product failure.** Its agent wrote "Does everything work now: yes" *and*
   "Leftover housekeeping (deliberately not done, it's a separate act)"; the classifier's FAILURE
   pattern matched the second sentence and returned `mixed`. The work was verified and **promoted**.
   This is audit entry 15 in [`V1.2-PLAN.md`](V1.2-PLAN.md), with the corpus-wide measurement in
   `tooling/probes/v12-claim-classifier-audit.mjs` — which also establishes that **no v1.2-era
   record is affected**, which is why no number above moves because of it.

## 3. The clean configuration, measured across four fixtures

Every paired trial above was run with `--register-requirements` on the guarded arm, where nothing binds
those requirements — a configuration the harness now **rejects** as a fixture's authored setting, and
whose trials are excluded from the agreement metric. That left a real gap: **the correctness axis had no
clean measurement on any v1.2 fixture.** It now has four, one per piloted fixture, in the declared
configuration (`guarded`, requirements **not** registered):

| fixture | category | plain tokens | **guarded (clean)** | delta | hidden / visible | Amabie verdict |
|---|---|---|---|---|---|---|
| `cli-exit-codes` | F | 198,068 | 313,018 | **+58.0%** | PASS / PASS | `READY` |
| `flag-clusters` | J | 88,664 | 451,017 | **+408.7%** | PASS / PASS | `READY` |
| `stub-completion` | D | 147,680 | 152,472 | **+3.2%** | PASS / PASS | `READY` |
| `duration-parse` | B | 105,007 | 243,663 | **+132.0%** | PASS / PASS | `READY` |
| **total** | | **539,419** | **1,160,170** | **+115.1%** | 4/4 PASS | **4/4 `READY`** |

**This is the first measurement in v1.2 taken in a configuration the harness accepts, and it says two
things clearly:**

1. **The completion path works.** All four guarded runs reached `READY` on work the sealed oracle also
   passed. That is the mechanism doing its job end to end — and it rules out a systematic harness
   failure as the reason the corpus shows no correctness advantage.
2. **It costs more than double: +115.1% model tokens over the plain arm.** Zero false dones and zero
   false greens in either arm, so **no correctness advantage was bought** with that cost.

**The contaminated numbers were misleading in Amabie's favour.** The earlier paired table showed deltas
of +2.7% to +155.7%; those runs were partly cut short by the Stop hook refusing, so part of what they
measured was the cost of a *refusal*, not of a completed verification. The honest figure is the worse
one. `stub-completion` is the one class where the overhead is near-neutral (+3.2%), which is the shape a
saving would need to have — but one fixture is not a finding.

n = 1 per cell, four fixtures, one model, one host. Not a rate, and nothing here speaks to other models
or larger repositories.

### The same measurement on three LEGACY fixtures — the overhead is task-dependent, not a constant

The four fixtures above are v1.2's own. To test whether `+115.1%` is a property of Amabie or of those
fixtures, the same clean configuration was run on three pre-existing fixtures and compared with their
stored `plain` baselines:

| fixture | plain (mean of stored runs) | guarded (clean) | delta | hidden / visible |
|---|---|---|---|---|
| `bug-sum` | 77,469 (n=20) | 84,087 | **+8.5%** | PASS / PASS |
| `multi-requirement-pricing` | 206,722 (n=9) | 304,291 | **+47.2%** | PASS / PASS |
| `spec-edges` | 145,118 (n=18) | 350,223 | **+141.3%** | PASS / PASS |

**Every one correct** — hidden and visible both PASS, no false dones — and the cost ranges from
near-neutral to more than double. Combined with `stub-completion` at +3.2%, the honest generalisation
is not "Amabie costs 2.15x" but **the overhead is task-dependent, and on these fixtures it is never a
saving**.

**Caveat that must travel with this table:** the `plain` figures are means over runs recorded in
EARLIER batches, not paired same-session trials, and the batch-to-batch variance is not controlled.
That makes these three deltas weaker evidence than the four paired rows above, and it is why they are
presented separately rather than merged into one headline.

What the seven fixtures together establish: **in the configuration the harness accepts, Amabie's
completion path is correct on every task tried, and it costs more than the bare agent on every task
tried — by an amount that depends heavily on the task, from +3.2% to +408.7%.**

## 4. Why the corpus cannot show an advantage — three measured reasons

These are findings about the harness and the corpus, not guesses:

1. **The traps are solvable.** Eight paired trials across four fixtures and five classes — every arm
   correct, no separation. (An earlier draft of this document said "nine"; the count is four fixtures
   on two arms, and it is stated as a count of arm-trials so it can be checked.)
2. **The one fixture class that ever produced a real false-done was never wired to the requirement
   mechanism.** `version-bump` — which `BENCHMARKS.md` credits with the only such class the corpus ever
   surfaced — declared **no** requirements, so `--register-requirements` was a no-op for it and the
   `per-requirement` duty never existed in its guarded trials.
3. **The comparison arm structurally cannot exercise the gate v1.2 built.** `run-trial.mjs`'s
   `guardedInstructions` never mentions `amabie work`, so the agent edits in place and the only gate
   that can fire is the Stop hook. The v1.2 `REQUIREMENT UNBOUND` handoff gate therefore **cannot be
   measured on that arm, for any fixture.** *(MEASURED SINCE, and this reason is now partly closed
   rather than only disclosed: the `workflow` arm — which does drive `amabie work` — was run on
   `bound-requirements`, the corpus's only fixture with BOUND requirements, and it registered,
   worked in the candidate, passed the bound checks and was promoted. See Section 2's `workflow`
   table. The gate is therefore measurable on that arm; it is still n = 1, and the `guarded` arm
   remains unable to exercise it.)*

## 5. A measurement defect found and fixed, and what it touched

Running the protected arm with `--register-requirements` while the fixture's requirements are bound to
nothing makes the Stop hook refuse **correct** work — measured at **217,799 tokens over 21 turns**, with
the hidden oracle passing. Every trial in that configuration was being counted in the benchmark's
**false-red headline**, which would have reported that Amabie refused correct results when the refusal
said nothing about the code.

Fixed at the site that feeds the metric, and audited rather than assumed:

| metric | affected? | why |
|---|---|---|
| **KPI verdict** | **no** | uses the token delta, `deliveredCorrect`, `falseDone` — none of which the configuration touches |
| false-green headline | **no** | requires `doctorExitCode === 0`; every contaminated trial had 2 |
| false-done counts | **no** | derived from the claim and the oracle |
| **false-red headline** | **yes — fixed** | all four satisfied `doctorExitCode !== 0 && deliveredCorrect` by construction; now excluded, with the exclusion counted and reported |
| token figures | **no** | the trials really spent those tokens; only the verdict was mislabelled |

The harness now (a) records the configuration on the trial, (b) excludes such trials from the
agreement metric, (c) warns on stderr, and (d) checks a fixture's declared `benchmarkConfig` — **both**
axes, arm and `registerRequirements` — against the run.

## 6. What this does NOT establish

- **No correctness claim.** Not at n = 1, and not on a corpus whose traps a plain agent solves.
- **No token claim.** The clean-configuration delta is **+115.1%** against Amabie (Section 3). The
  `+82.7%` in Section 2 is the contaminated-corpus aggregate and does **not** govern — quoting it here,
  in the section that disclaims token savings, would have been the wrong number in the right place.
  The v1.1 result of −19.6% came from bound requirements in a different configuration and is not
  reproduced here.
- **Nothing about other models, hosts, or larger repositories.**
- **No `HARDENED` claim.** See [`V1.2-PLAN.md`](V1.2-PLAN.md): the boundary measured **unavailable** on
  this host, and a first measurement of mine that claimed otherwise was retracted.

## 7. What the next corpus needs

The difficulty axis this repository still has not produced — the same three v1.1 named and two rounds of
fixture authoring did not reach: **longer horizon, weaker visible signals, or requirements whose
*places* are not all named.**

**The harness precondition was MET in Round 12, and meeting it changed what that corpus could say.** All 19
fixtures declare the configuration they are authored for (`{ arm, registerRequirements }`), and each
declaration is checked against the fixture rather than trusted:
`tooling/probes/v12-fixture-configurations.mjs` seals every fixture's project, registers that fixture's
own stated requirements, and requires `registerRequirements: true` **exactly where** the product's own
digests and sealed bindings show every requirement is bound. Exactly **one** fixture passes that test —
`bound-requirements`, with three requirements bound to three declared checks. For the other 18 the flag
derives duties nothing can discharge, which is why their declared configuration is the clean one, and
why "register the requirements" was never a measurement of the requirement machinery for them.

Two consequences for whoever writes the next fixture: (1) a fixture meant to exercise requirement
COVERAGE must **bind** its requirements, as `bound-requirements` does — declaring them is not enough,
and the probe will fail loudly if a declaration overstates what it measures; (2) the difficulty axis is
still missing, and a third round of the same fixture shape would be counting rather than measuring.

**Current bounded follow-up:** the tree now contains 20 fixtures and 29 v1.2 trial
records. `stateful-replay` adds one explicitly contracted stateful/cross-file
experiment with a sealed binding and one trial per arm. Both competent agents
passed all 406 hidden assertions; the workflow actually promoted. Zero false dones,
no demonstrated correctness separation. Exploration is frozen at that result.
See `tooling/benchmark/STATEFUL-REPLAY-EXPERIMENT.md` for records and scoring caveat.
