# Amabie v1.3 — product audit

**Status:** Phase A deliverable, with the first implementation slice landed and verified.
**Audited tree:** `main` @ `b7e2cae` (v1.2.0), clean worktree.
**Method:** every claim below is either (a) an executed measurement with the command or probe that
produced it, or (b) a `path:line` reading. Interpretations are labelled. Where a number does not
support the conclusion people would like to draw from it, that is stated in the same paragraph.

Three read-only audits were run against the v1.2 tree and are the source of the UX, token and
integration sections: the user-facing surface audit, the token-shape audit, and the agent-integration /
Cursor capability audit. The journey itself was measured with a new probe,
`tooling/probes/v13-journey-baseline.mjs`, which prints `PASS`/`FAIL` for the invariants this slice
establishes and `OPEN` for the gaps it deliberately does not close.

## CURRENT USER JOURNEY

Two disjoint journeys exist today, and **neither one is the journey the product promises.**

### A. The everyday journey (a completion gate that does not confine anything)

1. `npm install -g ./amabie-rn-cli-1.2.0.tgz` (Node ≥ 22).
2. `cd repo && amabie setup --yes`. Amabie detects the project, infers a verification plan from checks
   the project *already declares*, seals it, installs a Claude Code `Stop` hook into
   `.claude/settings.json`, and smoke-runs the plan. Measured output on a fresh Node repo: plan
   `✓ tests: npm run test`, smoke test exit 0, verdict `READY`, exit 0.
3. The user asks their coding agent to do something. **The agent edits files and runs shell with its
   own native tools.** There is no `PreToolUse` hook anywhere in the product; every edit happens before
   Amabie is consulted.
4. The agent says it is done → the `Stop` hook runs `amabie checkpoint` → the sealed plan runs → on
   failure the completion is **blocked once** (`stop_hook_active` then allows with a message).

So the default path is a *detector at the end*, not a guardian. Measured consequence: a normal agent
edits the base directly and `amabie doctor` answers
`READY — wiring verified; the checks just ran and passed, and no proof obligation is open.`

### B. The proven journey (real authority, all of it manual)

5. `amabie task "<intent>" --requirement "<each part>"` — the requirement list is human knowledge.
6. If any requirement has no sealed check: `amabie bind <script> --requirement "<exact text>" --reseal`.
   **This is an OPERATOR act**; an agent may not perform it.
7. `amabie work <name> "<intent>"` → prints a candidate directory → work only there → `git commit`
   there → `amabie finish <name>`.
8. Subjective duties: `amabie accept <name>`, typed in a real terminal.
9. Cleanup: `amabie isolate --remove <name>`.

There are **20 commands** in the CLI. Two interactive prompts exist in the whole product (the setup
smoke-test `[Y/n]`, and the acceptance name-typing). There is **no per-command help**: `amabie setup
--help` *runs setup and writes*, `amabie doctor --help` *runs the checks*; only `mcp --help` behaves.

### CORRECTION — a claim in the first draft of this audit was wrong, and measuring it changed the plan

The first draft recorded, as friction #5 and as the probe's `OPEN` finding, that *"an agent that edits
the base directly is told `READY` while the candidate route can refuse"* — i.e. that the default path
accepts a green suite as done. **The observation was accurate; the inference was not.** Section F of
the journey probe measures the completion gate directly, by invoking `amabie checkpoint` exactly as
the harness does, and the result is the opposite of the inference:

| everyday case (direct edit, no candidate) | measured verdict |
|---|---|
| behaviour change **with** a check the sealed plan can discriminate | `ALLOW` (silence — the documented "nothing needed" signal) |
| behaviour change **no declared check can see** | **`BLOCK`: "Amabie blocked completion: NOT PROVEN — the sealed checks pass on the base commit too, so they carry no evidence about this change (greeting.cjs)"** |
| docs-only change (no behaviour moved) | `ALLOW` |

The earlier fixture had changed **both** the source and the test, so the plan genuinely discriminated
the change — the `READY` was *earned*. `discriminationObligation` (`onboarding.ts:1315`) is applied
unconditionally on the checkpoint path (`onboarding.ts:2817`), so the product's most important
invariant — *a green suite that cannot tell the change from the base proves nothing about it* — **is
already enforced on the path every ordinary user is on.**

Two consequences, both of which change what v1.3 should build:

1. **The everyday path is closer to "just works" than the first draft claimed.** `setup --yes` once,
   then use your agent normally, and an undiscriminated change is refused. The remaining everyday gap
   is the missing *lifecycle* (no isolation, no frozen task authority, no promotion of exact verified
   bytes) — a product gap, not a trust hole, and largely inapplicable to a user editing their own
   repository.
2. **The highest-leverage remaining work is therefore NOT closing a false-acceptance hole.** It is
   moving the *timing*: today the gate speaks only at the end, so the agent cannot ask "am I done?"
   mid-flight and instead runs its own verification campaign (~36 of 57 execs). Giving the agent
   Amabie's verdict **as a tool, wired by `setup`**, is what serves criteria (3) and (4) together.

The probe now asserts all three cases (`F1`/`F2`/`F3`) so the corrected reading is the one under test,
and records the narrower lifecycle gap as the sole `OPEN` finding.

## TOP TOKEN COST SOURCES

Measured from the retained transport logs of the v1.2 pilot (Amabie arm 585,337 tokens on
`stateful-replay`; plain arm 212,777).

**The shape, first, because it is the whole story:** plain pays a large *constant* per turn
(~12.2–12.6 K, its own system prompt and six native tool schemas) and adds almost nothing — its cost is
linear in turns. The Amabie arm pays a tiny constant (~600) but adds **~2,350 tokens of its own
content per turn**, which every later turn re-reads — its cost is quadratic. That is why the same arm
wins by 84 % on a 6-turn task and loses by 175 % on a 22-turn one.

| # | Source | Size | Mechanism |
|---|---|---|---|
| 1 | **The model's own output, re-read on every later turn** | output 39,351 tokens (4.9× plain's 8,002); × ~10.5 re-reads ≈ **413 K ≈ 70 %** of the run | The confined tool has **no edit primitive** — the schema is exactly `list\|read\|write\|exec` (`worker-tools.ts:31-33`). Every change re-emits a **whole file body inside the assistant message**, which then lives in history forever. Measured: `src/api.js` (979 B on disk) written **9×**. |
| 2 | **Tool-result payloads, appended and re-read the same way** | 49,329 B over 21 results ≈ **22 %** | `exec` returns the whole stdout *and* stderr, `read` the whole file — no truncation anywhere (`production-tool.cjs:31-44`) — plus ~323 B of `observation` boilerplate on **every** call. The largest results are the model's *own* test runs (max 8,739 B), not fixture files. |
| 3 | **Turn count as the multiplier** | 22 turns vs plain's 18; **45 turns / 917,504 tokens** before the batching change | Each turn pays the entire accumulated context. Turns grow when the model runs things — and the model runs things because it cannot otherwise know it is done. |
| 4 | **Fixed per-request overhead** | Amabie ≈ 600 × 22 ≈ **2 %** — negligible. Plain ≈ 12.2–12.6 K × 18 ≈ **210 K of its 212,777** | Plain's cost is almost entirely its own base context. This is the constant the Amabie shape trades away. |

**Three things the recorded data does not support**, stated here because they are the claims most
likely to be repeated:

- **The +54.4 % is not a property of "Amabie".** n = 1 per Amabie cell; the arms differ in tool
  surface, system prompt (`--bare`), memory (`--setting-sources ''`), prompt text and day; the plain
  arm is a *recorded* run, not a paired one; `stateful-replay` is 92.5 % of the Amabie total.
- **In money it is worse than in tokens: +110.6 %**, not +54.4 % (recorded `costUsd` $0.8414 →
  $1.7723), because cache reads bill at a fraction of output and the Amabie arm is output-heavy
  (43,338 vs 12,848 output tokens).
- **"Cache-read is 83 % waste" is wrong** — plain's cache-read share is *higher* (85.4 %). Only
  `turns × content` is actionable.

## WHAT CAN BE MADE AUTOMATIC SAFELY

The test applied to each item: *can Amabie establish this objectively from the repository or from the
human's own words, without inventing a duty or dropping one?*

**Safe, and now automatic:**

- **Project, package manager and verification-plan discovery.** Already fully automatic: lockfile →
  pm; `test`/`typecheck`/`build`/`bench`/`e2e` script names → plan kinds; Python/Rust/Go adapters; a
  universal contract that anchors on Makefile/justfile/Task/Composer/CI `run:` lines with an explicit
  anchor-strength label. Discovery *invents nothing* — a tool named in a comment is not a declaration.
- **Inferring the KIND of work from the human's own words** (slice 1). Safe because kinds only ever
  **add** duties, never remove one: `TaskIdentity.kinds` is a union and a mislabel adds work. Widened
  narrowly to words that **assert brokenness** rather than merely name a topic — see Security risks.
- **Refusing a task at handoff when nothing could judge it** (slice 1). Strictly fail-closed: it
  refuses *earlier* than `finish` did, opens nothing, launches nothing, spends nothing.
- **Reporting whether the completion hook is actually installed** (slice 1). A state answer, not a
  verdict; it can only ever claim less.

**NOT safe — must stay human or operator:**

- **Auto-binding arbitrary prose requirements to arbitrary checks.** "Add email validation" bound to
  `npm test` would manufacture proof that does not exist. Which sealed check measures *which* stated
  requirement is a semantic judgement, and it is the operator's act by design.
- **Defaulting a kind when inference finds nothing.** A wrong kind adds a duty the change cannot
  discharge — a `bugfix` duty demands a base-vs-candidate discrimination, which a docs-only change
  cannot produce. That is a false *block*, and worse, it would be Amabie inventing the authority to
  judge. Refusing and asking one question is the honest ending.
- **Closing a subjective duty.** Aesthetics and "feel" stay `amabie accept`, in a terminal.

## WHAT STILL REQUIRES HUMAN JUDGMENT

1. **Which check measures a stated requirement** — the binding act. A wrong binding is fake proof.
2. **Subjective acceptance** — "does this look right", by construction, in a terminal.
3. **Waiving the discrimination rule** — when a change legitimately cannot be told from the base.
4. **Approving a project's hooks the first time** inside Claude Code (the harness's own consent gate).
5. **The first-time decision to protect a repository at all** (`amabie setup`).

That is five decisions, and only the first two are recurring. Everything else Amabie can answer.

## WHAT THE AGENT CURRENTLY DOES THAT AMABIE SHOULD DO

Measured, on the stateful fixture, from the model's own exec operations:

- **~36 of 57 execs were the model re-running its own checks and tests** (`node --test-reporter=dot
  tests/contract-*.cjs` ×16, `node tests/contract-extra.cjs` ×11, `node checks/contract.cjs` ×4,
  `node run-tests.js` ×3, …). The plain arm ran **5 shell commands total**.
- **The model authored its own verification apparatus as whole-file writes** — `tests/contract-extra.cjs`
  ×3, `tests/contract-fuzz.cjs`, a `drive-tmp.cjs`, and a `tmp-mut` mutate/restore rig driven by 19
  `cmd /c` operations. Twelve tool-call lines carried 58,587 bytes of write payload (~37 % of the
  arm's text output).

This behaviour is **rational**: the model cannot otherwise know whether it is done. Amabie should
absorb it by handing back a **short trusted verdict** instead: which check ran, its status, the first
failing assertion, the digest, and the path to the full log — the pattern the product already proves
works, since the Stop hook's failure payload is 308 characters where the block it replaced carried up
to 4,000.

**The constraint that governs this whole section, from this repository's own measurements:** the arm
that was told *not* to verify produced a **false done and a false green**. Suppressing the agent's
self-verification is the wrong lever. The replacement verdict must be **at least as informative and at
least as trusted** as what the agent produced for itself, or correctness is being traded for tokens —
which the priority order forbids.

## PROPOSED EVERYDAY WORKFLOW

```
once per repository:   amabie setup --yes
thereafter:            use your coding agent normally
```

Target: **zero Amabie commands typed by the human**, for ordinary objective work.

Amabie is responsible for, invisibly: discovering the project and its checks; sealing the plan; wiring
the harness hook; isolating the change; running the sealed plan outside the model's context; promoting
only verified bytes; and telling the agent **one line** — `PASS`, or `FAIL: <short actionable
reason>`. The human is interrupted only for the two recurring judgements above.

Today the honest count is **three commands** (`setup`, `work`, `finish`) plus one human decision per
task that names no kind. The gap between three and zero is the agent-integration work, not a wording
change.

## PROPOSED EXPERT WORKFLOW

**Unchanged, deliberately.** `task` / `bind --reseal` / `isolate` / `isolate --verify` /
`isolate --promote` / `accept` / `provider …` remain the trust boundary and keep their vocabulary,
their exit codes and their `--json` envelopes. Everyday mode is a *presentation and orchestration*
layer over them — it must never be a second implementation of a gate, because two implementations is
two places for a gate to be weakened.

New in v1.3: `--verbose` becomes the door to the machinery, and every everyday refusal names the
expert command that resolves it.

## CLAUDE CODE INTEGRATION PLAN

**What exists:** one `Stop` hook written into `.claude/settings.json` (`node "<cli>" checkpoint`),
added by merge, never overwriting; backed up before writing; atomic; exactly removable by
`amabie uninstall`. It can block a completion **once**, and it fails *open with an honest message*
(never a fake green) when the config is corrupt, distrusted or the plan is empty.

**Plan, in order of leverage:**

- **A. Keep the completion gate.** It is the only mechanism that can *refuse* today, and Cursor can
  inherit it (below).
- **B. Give the agent a verification TOOL, not a lecture.** **DONE in slice 2** — `amabie setup` now
  registers `amabie mcp` in the project's `.mcp.json`, so the agent can call `amabie_doctor` and get
  Amabie's verdict instead of authoring its own verification campaign. This is the single change that
  removes the ~36 self-run checks and their whole-file test apparatus from the model's context. The
  measured analogue in this repository's own corpus: arms that removed the model's check-running
  measured **−31.8 %** and **−58.5 %** tokens with correctness unchanged. The win is **projected, not
  measured** — whether the agent uses the tool rather than its own tests is a model-choice question and
  must be measured, not assumed (v1.2's optional-batch experiment failed by assuming exactly that).
- **C. Productise the confined transport.** The confinement already exists and is measured
  (`provider model-transport`: `--bare --restricted --tools '' --strict-mcp-config --setting-sources ''`,
  one tool, AppContainer + restricted token + zero capabilities + low integrity, with a broker that
  authenticates the caller by measuring its kernel token). It is today an 8–9 step operator ritual
  ending in a batch run from a prompt file. The product gap is **one command** that starts the agent
  under it.
- **D. Do not claim more than is true.** Claude Code's native tools cannot be removed by an MCP server,
  so on the default path the writes are unconfined. The `model CLI process itself` is not confined
  either — only its tool calls cross the boundary — and the existing probe measures the *advertised*
  tool list, not that the CLI cannot act natively. Both facts belong in the docs, and `HARDENED` stays
  unreachable until the measured deployment exists.

## CURSOR INTEGRATION PLAN

Researched from Cursor's own documentation. **The premise "Cursor offers only MCP" is out of date**,
and one finding changes the plan:

- **MCP servers are supported** (stdio/SSE/HTTP; `.cursor/mcp.json` + `~/.cursor/mcp.json`; one-click
  install; an extension API registers them without touching config).
- **No documented way exists to remove Cursor's native tools in the IDE.** Native edits are explicitly
  ungated — Cursor states agents "can modify workspace files without approval". So an MCP tool surface
  would be **additive**, and **MCP-only confinement is not achievable in Cursor today**. Only the SDK's
  `tools`/`disallowedTools` can switch built-ins off, and it is local-only and drives the loop from
  Amabie's own process.
- **Cursor imports Claude Code hooks**, including `Stop` → `stop`, and honours a flat
  `{"decision":"block","reason"}` as an automatic follow-up. Third-party hook import is **on by
  default**. That makes the existing `amabie setup` hook a plausible **zero-new-code completion gate
  for Cursor.**

**Plan:**

1. **Claim nothing until it is measured on a real Cursor install.** Two unknowns decide whether the
   import is actually a gate: Cursor's `stop` input is documented as `{status, loop_count}` while
   Amabie derives the repo from `input.cwd` and keys its one-repair guard on `stop_hook_active`
   — whether Cursor synthesises those fields for imported Claude hooks is **undocumented**; and the
   default `loop_limit` for Claude-format hooks is `null` (no cap), so a mis-mapped guard could loop
   instead of stopping. Measure, then document.
2. **Teach `setup` to recognise Cursor.** Today it does not, and on a machine with `~/.claude` present
   it will report the Claude Code integration even when the user's agent is Cursor.
3. **If a real edit gate is wanted later**, the documented primitive is narrow: a Cursor Plugin
   (marketplace-installable, no hand-edited config) shipping a `preToolUse` hook on `Write`/`Shell`
   with `failClosed: true` and BOM-tolerant stdin parsing. That is a **permission gate on writes, not
   confinement** — Amabie cannot put Cursor's native tools inside the AppContainer.
4. **Never claim HARDENED on any Cursor path.**
5. **Do not build a Cursor-specific architecture.** Cursor is the second consumer of one engine
   (`result`/`doctor`/`work`/`finish` over MCP), not a second engine.

## TOKEN ARCHITECTURE PLAN

Ranked by measured size of the mechanism it attacks. All win figures are **arithmetic projections**
from the measured totals — estimates, not measurements.

| # | Change | Attacks | Est. win | Trust cost |
|---|---|---|---|---|
| 1 | **An `edit`/`patch` primitive** (anchored replace or line-range), so a change is a patch and not a whole file body in the assistant message | #1 (70 %) | **≈ −35 %** on the dominant cell | A **new mutation authority inside the boundary**; needs the full escape battery re-run |
| 2 | **A trusted, compact "what do the project's own checks say" operation**, returning `{check, status, firstFailingAssertion, digest, logPath}` | #3 and its cause | **≈ −30 to −45 %** | Must be **broker-produced**, provenance-carrying, never model-writable, and must not read as "stop working" |
| 3 | **Short structured verdicts + digests instead of raw payloads** (`exec` → status/bytes/sha256/first failure line/artifact id; full log retrievable by explicit expand) | #2 (22 %) | **≈ −18 %** | Truncation can hide the failing assertion; digests must be computed **inside** the boundary; the artifact store is a new trusted path the worker must not write |
| 4 | **Cap and summarise `exec` output** deterministically (head + tail + elided count + digest + log path) | #2 | ≈ −7 % | Bounded: always keep exit status, first failing line, and a retrievable full log |
| 5 | **Compound `edit+check`** as one operation, collapsing write→run→read→decide into one decision | #3 | not projected | Low — same authority plus a check invocation |

**Two rules from the data that constrain every row above:**

- **Batching quantity is not the lever.** bug-sum won −61.5 % at 2.14 ops/call; bound-requirements won
  −83.9 % at 4.00 ops/call; stateful-replay **lost 175 % at 4.67 ops/call** — the most-batched cell is
  the worst cell.
- **The winning lever is content, not turns alone**: stop putting whole file bodies and unbounded
  command output into the model's own message history, and remove the *reason* the model runs its own
  verification campaign.

**Measurement hygiene, without which none of the above can be believed** (all cheap, all required
before a v1.3 token claim): run the plain arm **paired in the same session** instead of reading
another day's record; record the plain baseline path inside the pilot record (the current default path
does not exist on disk); archive transport logs per run (the pilot overwrites one temp filename);
n ≥ 3 per Amabie cell (every Amabie cell today is a single trial); store the prompt **actually sent**;
and log a per-request context size from the provider side, since the CLI's per-message usage is
partial and the trajectory is currently unmeasurable.

**Standing target:** ≤ 75 % of plain on a representative executable benchmark. On the evidence
above, reaching it requires rows 1 and 2 — the two changes that remove content from the model's
context. Nothing in the recorded data suggests prompt wording can get there.

### MEASURED UPDATE — row 1 is implemented, and the target's binding term is NOT what this table implies

`edit` was built and measured (`tooling/benchmark/results/v13p1-edit-primitive-measurement.md`). Three
findings, all from executed runs, and one of them changes the plan:

1. **The mechanism works.** A representative change costs **141 B as an `edit` versus 1815 B as a
   `write` — 8 %** — measured through the real AppContainer, with containment proven unchanged
   (absolute path, traversal and the sealed authority are all denied, victims byte-unchanged) and
   ambiguous anchors refused rather than guessed.
2. **The model chooses it** — which was the open question, because this repository has already made the
   opposite mistake once (an optional `batch` primitive used zero times in 50 calls). On a small real
   task through the real confined transport: `{"list":2,"read":3,"edit":1,"exec":3}` — **edit 1,
   write 0**, 616 bytes of its own output for a 2,499 B source file, defect fixed and confirmed from the
   trusted side.
3. **It is not sufficient, and the table above now looks wrong.** On the stateful stress test the
   model's own output fell **39,351 → 30,504 (−22.5 %)** — exactly the term row 1 attacks — and the
   TOTAL did not improve: **595,419 vs v1.2's 585,337 (+1.7 %, i.e. noise)**, against plain's 212,777.
   Correctness held at 406/406 both sides.

The reason is in the same table: **cache-read is 87 % of the total and is driven by `turns ×
accumulated context`.** Turns went 22 → 24, so a 22 % smaller turn was cancelled by two more turns.
**The binding term is turn count, not bytes per write.** Rows that reduce bytes (this one, and the
output cap in row 4) cannot reach the target alone; rows that reduce TURNS (2 and 5) are the ones that
can. And even the adoption is task-shaped: on the long run the model still issued **10 whole-file
`write`s against 4 `edit`s**, because it regenerates files it is still designing — so the next step is
to make the compact form the ONLY form for changing an existing file, not merely the cheaper one.

**Nothing about the token target is claimed as achieved.** The honest sentence is: *output per turn fell
22.5 %; the total did not move.*

1. **The everyday shape is the ONLY Amabie configuration cheaper than working without Amabie — 92.7 %,

   does it ("verification is automatic; you will be told what to fix; do not re-read output or repeat a
   check you have just run") is now shipped through Amabie's own two agent channels (`amabie mcp`'s
   initialize instructions and the advisory `AGENTS.md` block), with the RELIABILITY half kept because
   the aggressive variant that forbade self-verification measured a false done **and** a false green.
2. **The ceremony is what costs.** `work` → `finish` is **+77.8 %** — nearly twice the everyday shape —
   *with identical correctness*. So v1.3's zero-ceremony goal and its token goal are the same goal, and
   `work`/`finish` are confirmed as an EXPERT surface rather than the ordinary path.
3. **The long task does not explode on the everyday shape** (17 turns, 96.1 % of plain). The explosion
   belongs to the transport configuration, not to "Amabie on a long task".

**≤75 % is still not met by any recorded configuration**, and the honest claim is the measured one:
Amabie's everyday shape costs about the same as working without it while catching work a green suite
cannot discriminate; its confined transport makes short tasks 2–6× cheaper and long ones more expensive.

### MEASURED UPDATE 3 — the `plain` arm was NOT wired, and Amabie's per-turn footprint cannot reach the target

**Correction first, because MEASURED UPDATE 2 above states the opposite.** This audit claimed

— which `plain` is not in, and the harness says so again at line 803 ("the plain arm HAS no Amabie").
`plain` gets no seal, no Stop hook and no MCP entry.

The correction **strengthens** the headline rather than weakening it: 92.7 % is not "two Amabie
configurations differing by a prompt paragraph", it is **Amabie's everyday shape against genuinely not

**Second measurement — what Amabie costs on every turn, used or not** (`tooling/probes/v13-standing-context.mjs`).

| | bytes |
|---|---|
| instructions | 1,475 |
| tool definitions (6 tools) | 4,251 |
| **standing payload, per turn** | **5,726** |

At ~1,432 tokens/turn (bytes ÷ 4 — a derived figure, not a measurement) and 17 turns, that is ≈24,300

claim otherwise: the remaining ~17 points would have to come from the agent doing materially less work,

### MEASURED UPDATE 4 — the everyday path cannot reach ≤75 %, and the general claim that nothing can is retracted below

MEASURED UPDATE 3 showed the target cannot be reached by trimming Amabie's *footprint* (~2 points
available). The remaining route was the agent doing less work, and since cache-read of accumulated context
dominates, "less work" means "fewer turns". Exactly one thing on the everyday path ADDS turns: the
completion gate refusing a finish, telling the model why, and the model running again.

That question needed no new trials — every recorded trial was already paid for. `tooling/probes/v13-gate-cost.mjs`
reads the 565 stored trial records (324 of them in a gated arm) and reports:

| | |
|---|---|
| gated completions that recorded a block | **38 / 321 = 11.8 %** |
| blocked runs | 17.5 turns, 339,462 tokens (n=28) |
| not blocked | 11.4 turns, 216,189 tokens (n=228) |
| overall gated mean | 12.1 turns/run (n=256) |
| extra turns a blocked run costs | 6.0 |
| expected saving if the retry vanished | 6.0 × 11.8 % = **0.71 turns = ~5.9 % of turns** |

**That 5.9 % is an upper bound on an impossible act.** It assumes every block's retry disappears while the
refusal still reaches the model — i.e. it removes the turns the gate costs while keeping the protection
that justifies them. And the confound is stated in the probe rather than buried: a blocked run may be
blocked *because* it is harder, so "blocked runs cost more turns" is not proof the gate caused them. The
load-bearing number is the block rate, which is a plain count.

**Put together, the two measurements bound what is available on the everyday path:** ~2 points of
footprint plus a ≤5.9 % turn saving that cannot actually be collected. Even the impossible sum lands near
**92.7 % → ~85 %**, not 75 %. The block rate is low (11.8 %) because the everyday shape already tells the
model that verification is automatic — the shape is *working*, and a working gate that rarely has to
refuse is not a cost centre to optimise.

**So the everyday path cannot reach `≤ 75 %` by any change that preserves the gate.** Both routes were
measured, not assumed; the first was found by measuring a claim this audit had asserted without checking,
and the second by reading data already on disk instead of buying a pilot. On the everyday path, reaching
75 % would require the agent to do materially less work than plain, and the only mechanism that does that
is not verifying — which is the false done and false green this product exists to prevent. **Do not trade
the gate for the number.**

**But this audit stated that conclusion too broadly and has to retract the general form.** It said `≤ 75 %`
is "not reachable by any change that preserves the gate". That generalises from the everyday shape to
every Amabie configuration, and the recorded corpus contradicts it: the **confined transport** is a
gate-preserving configuration sitting at **20,472 (16 % of plain)** on `bound-requirements` and **26,970
(38 %)** on `bug-sum`. A shape far under 75 % therefore exists, and the criterion is a target the project
can conceivably hit — it is not the impossibility the previous paragraph implied.

**What stops it is one fixture, and the explosion is now diagnosed rather than described.** On
`stateful-replay` the same transport costs **595,419 (280 %)**. Same task, same model, same starting bytes:

| arm | turns | output | cache-read | cache-create | total | cache-read/turn |
|---|---|---|---|---|---|---|
| `plain` | 18 | 8,002 | 181,639 | 23,070 | 212,777 | 10,091 |
| `guarded` (everyday) | 17 | 10,172 | 168,447 | 25,775 | 204,454 | 9,909 |
| confined transport | 24 | 30,504 | 518,099 | 45,715 | 595,419 | **21,587** |

Three facts fall out of that table:

1. **cache-read is 87 % of the bill** (518,099 of 595,419). The cost is not output; it is re-reading the
   accumulated conversation on every turn. Note what is *not* the difference, because it is easy to
   misread: plain's cache-read share is **85 %**, so the share is simply what an agent transcript costs.
   The confined arm is expensive because its context per turn is bigger (point 2), not because its share
   is unusual.
2. **The confined worker carries 2.1× the context per turn** (21,587 vs plain's 10,091) and emits **3.8×
   the output** (30,504 vs 8,002). Its own bytes land in its own context and are then re-read ~20 more
   times, so an extra kilobyte of output costs far more than a kilobyte.
3. **The `edit` primitive moved output but not the total.** MEASURED: output fell 39,351 → 30,504
   (−22.5 %) and the total did not move (585,337 → 595,419) — because turns rose 22 → 24 over the same
   change. Two effects cancelled; the primitive is not the lever on its own.

**The root cause is that the confined worker is launched ONCE and never told a verdict.** The pilot record
carries `workerLaunches: 1`, and the broker review and promotion run only *after* the worker has exited. The
worker therefore has no way to learn whether its work passes, and the recorded behaviour — ~36 of 57
`exec` calls re-running its own checks, plus a self-authored 58,587 B fuzz rig — is **rational**: it is the
only verification the worker will ever see. The everyday shape does not have this problem because its Stop
hook blocks *inside the session* and tells the model what to fix, which is exactly why it stays flat on the
same fixture (96.1 %).

**That diagnosis killed a change this round before it shipped, and the near-miss is worth recording.** The
plan was to add the everyday instruction — "verification is automatic, you will be told what to fix" — to
the confined transport's tool description, on the theory that the missing instruction caused the redundant
self-verification. In that transport the sentence would have been **false**: nothing tells the worker
anything. It would have been a claim shipped into the product that the product does not honour, which is
the precise failure this repository exists to prevent. Reading `workerLaunches: 1` first is the only reason
it was caught.

**So the next slice is a feedback loop, not a sentence — and where it goes is not obvious, so it is
specified.** The first version of this paragraph said the transport should "return a verdict to the worker
from the trusted side after a worker call". That is wrong about the process boundary, and the correction
matters because verification placed in the wrong process would be a second, weaker gate rather than the
existing one: `apps/cli/src/provider/model-transport.ts` registers the worker's MCP server **inside** the
confined launch (`--bare --restricted --tools '' … --mcp-config`), so `provider worker-tools` and the
`productionTool` handler it calls both run **under the confinement the worker is confined by**. The tool
handler therefore cannot be where verification happens — nothing inside that boundary can reach the trusted
environment, the trusted directories, the sanitized env or the pre-gates that the real verification owner
uses. A "verify here" call added inside the handler would be the worker's own process judging the worker's
own workspace.

The loop belongs at the **driver**, outside the confinement. Two constraints stay non-negotiable: the
verdict must come from the existing verification owner (`isolate --verify` and its environment), never from
a second implementation of a gate; and it must be produced from bytes the trusted side read itself.

**But a re-launch loop is NOT the fix for this explosion, and the previous draft of this paragraph was
wrong to propose it.** Two facts in the records settle it:

- **The worker SUCCEEDED on its single launch, both times.** `v13edit-…` and `v12p4-forced-…` both record
  `review: 200`, `promote: 200` and `deliveredCorrect: true`. A retry loop would never have fired on either
  run, so it cannot be the thing that lowers their cost.
- **A re-launch loop gives the ORCHESTRATOR a retry, not the WORKER intra-run feedback.** Within its launch
  the worker still cannot learn whether it is right, so it still has every reason to verify exhaustively —
  which is exactly the behaviour that costs 2.14× plain's context per turn. The loop would change what
  happens *after* an expensive run, not the expense.

**What the evidence actually points at is feedback the worker receives WITHIN its run.** The measured
behaviour is the tell: ~36 of 57 `exec` calls were the worker re-running its own checks, one question at a
time, and it then wrote a 58,587 B rig so it could stop asking. Every one of those was a round trip spent
buying information the tool result could simply have carried. So the candidate fix is: after an `implement`
batch, run the project's **own declared test command** in the workspace and return a compact result
alongside the operation output.

That design is deliberately the *narrow* one, and the narrowness is what makes it safe:

- **It adds no capability.** The worker can already run those tests itself — it did, 36 times. The change
  moves a call the worker is already making into the result it is already receiving.
- **It makes no trusted claim.** The result is the project's own test output, not an Amabie verdict, so it
  cannot mint a `PASS` and does not touch `NO PROOF, NO DONE`. The trusted gate still runs afterwards and
  is still the only thing that decides.
- **It is why the process boundary matters.** This is the one thing that *may* run inside the confined
  handler precisely because it grants nothing: it is the worker's own project, in the worker's own
  workspace, doing what the worker is already permitted to do. Verification must not follow it in there.

**The wall-clock objection to this design was raised here and has now been REFUTED by measuring it.** The
first version of this paragraph withdrew the per-batch design on the grounds that it "would time the run
out". That rested on an assumption written into the analysis as though it were a fact — *"a suite that takes
a minute"* — and the assumption had never been measured. Measured
(`tooling/probes/v13-transport-suite-cost.mjs`, materialising the fixture the way the harness does):

| | measured |
|---|---|
| the fixture's declared check (`node checks/contract.cjs`) | **45–47 ms per run** |
| running it after every one of the recorded run's 23 tool requests | **1.0 s** |
| that as a share of the 15-minute ceiling | **0.1 %** |
| headroom the recorded run actually had | 90 s |

So the per-batch design costs about **one second** against ninety seconds of headroom, and the wall-clock
objection does not hold. The reasoning error is worth naming because it is the same one this audit keeps
catching: the worker's 36 `exec` calls each cost a **model turn** (~34 s at the recorded pace), which is
what made the suite *feel* expensive. The suite is nearly free; the round trips around it are not — which is
precisely the argument FOR returning its result automatically. The ceiling facts above remain true and
matter on their own (the run really is at 92 %), but they no longer close this design.

**The token benefit was measured, and the first reading of it was WRONG — a single run is not a measurement.**
The design is built (slice 20, opt-in behind `AMABIE_CONFINED_CHECK=1`) and verified by
`tooling/probes/v13-confin-check.mjs`. Four runs now exist on `stateful-replay`, same fixture, model,
transport and hidden oracle:

| run | configuration | turns | total | wall clock | hidden oracle |
|---|---|---|---|---|---|
| v12p4 | neither change | 22 | 585,337 | 13.78 min | 406/406 |
| v13edit | neither change | 24 | 595,419 | 13.50 min | 406/406 |
| v13check | + per-batch check | **19** | **288,942** | 6.94 min | 406/406 |
| v13write | + per-batch check + create-only `write` | **32** | **842,597** | — | 406/406 |

**The −51.5 % this audit previously announced was read off ONE run, and the fourth run shows why that was
not safe.** Two consequences, both recorded rather than smoothed:

- **The create-only `write` change (slice 25) is REVERTED.** It was a correctness fix — the description says
  `write (CREATE a file)` and the implementation overwrote — but enforcing it measured **842,597 tokens and
  32 turns against 288,942 and 19**, and the mechanism is plausible rather than mysterious: a refusal costs
  the worker a round trip, and every later turn re-reads the extra exchange. A contract fix that costs
  2.9× is not a fix worth shipping unmeasured, so the enforcement is gone, the description is back to what
  the tool does, and `v13-confin-check.mjs` G1 now pins the CURRENT behaviour with the number beside it, so
  re-attempting it is a deliberate act rather than an accident.
- **The per-batch check's benefit is UNREPLICATED.** One run at 288,942 against two consistent baselines at
  585,337 and 595,419 is a large effect, but n = 1 is n = 1, and this cell has now produced 288,942 and
  842,597 for two configurations that differ by one guard. Until replicates exist, the honest statement is
  that the flag's effect is **not established** — which is exactly why it stays opt-in.

The mechanism originally diagnosed (cache-read dominating, the worker buying the same information one round
trip at a time) is still the best explanation for the 288,942 run, but an explanation that fits one point is
a hypothesis, not a result.

**THE AGGREGATE THIS AUDIT PREVIOUSLY QUOTED (82.1 %) IS WITHDRAWN.** It was not a single consistent
measurement: it took the long task from a flagged run at 288,942 — now known to be unreplicated — and added
two short fixtures measured WITHOUT the flag (20,472 + 26,970). Mixing a treated cell with untreated ones
and building a headline on one run is how a benchmark stops meaning anything. The number to quote is
whatever the full benchmark reports, run as one consistent pass; until then this audit states no aggregate.

The earlier reasoning about what remained ("the worker emits 2.9× plain's output, so the next lever is its
own bytes") led to **slice 25, which is now REVERTED with its measurement recorded**: enforcing `write` as
create-only cost **842,597 tokens and 32 turns against 288,942 and 19** on the same cell. The contract
mismatch it fixed is real — the description says `write (CREATE a file)` and the tool overwrites — but the
fix as implemented was a large regression, plausibly because a refusal costs a round trip and every later
turn re-reads the extra exchange. The enforcement and its description text are gone; `v13-confin-check.mjs`
G1 pins the current behaviour with those numbers beside it so the next attempt is deliberate.

**The flag stays off by default**, which is now doubly justified: the benefit is unreplicated, and the cell
that produced it also produced 842,597 for a configuration one guard away. A default-on decision needs
replicates, not a promising run.

That leaves the second idea, which the arithmetic also supports: **a single run's cache-read grows with the
square of its turns, and its wall clock grows with them too, so partitioning one long run into a few shorter
runs with fresh context (and only a compact hand-off between them) attacks both terms at once.** It is NOT
proposed and NOT claimed — it requires the task to be decomposable, which nothing here has established. It
is recorded so it is not re-derived later.

`workerLaunches` therefore stays 1 for a passing run, and the probe's `A1`/`A3` assertions remain the
guardrails: nothing in that handler may become a gate.

If the arithmetic holds — and it is arithmetic, not measurement — bringing the long task to plain's level
would put the aggregate at **260,219 = 63.5 % of plain**, under target with the gate intact. Nothing here is
claimed until a pilot says so, and the pilot is deliberately not run until the per-batch feedback exists to
measure.

### MEASURED UPDATE 5 — the everyday path CAN be told mid-task, and the lever is real but too small (bounded below)

The confined transport's measured saving came from one move — the worker is handed its project's own
check result instead of spending a round trip to ask for it (single-fixture evidence: see MEASURED UPDATE 6's
replication table for what it is and is not worth). **The everyday path — the shape v1.3 actually ships, and the
one sitting at 92.7 % of plain — has no equivalent.** Its `Stop` hook speaks only at the end of a turn, so
mid-task an agent that wants to know whether its change works must decide for itself to call
`amabie_doctor`, or re-run the checks itself. The same waste is available there, on the shape that matters
most.

Claude Code documents a `PostToolUse` hook whose `additionalContext` is "added to Claude's context alongside
the tool result". A documented field is not evidence that it is delivered — this repository already lost
time to exactly that assumption with `--strict-mcp-config` — so it was measured, on this host, with the real
CLI (`tooling/probes/v13-posttool-feedback.mjs`, 27,642 tokens):

- a throwaway project ships a check that rejects anything but `two`, and the agent is asked to write `one`;
- a `PostToolUse` hook (matcher `Edit|Write|MultiEdit`) runs that check and plants a MARKER beside its real
  output in `additionalContext`;
- **the model repeated the marker back verbatim, together with the check's exit status and its failure
  text**, having no other way to know either.

So mid-task feedback is available on the everyday path, and the mechanism is not in doubt. What is NOT yet
established is whether it is worth having, and the honest concerns are recorded rather than waved away:

- **Wall clock is the risk, and here it cannot be waved away as it was in the confined case.** That case was
  affordable because the fixture's check measures 45 ms (MEASURED UPDATE 4). A real project's suite may take
  minutes, and a hook that runs it after *every* edit would make the everyday experience slow — trading the
  release's central promise for a token win. **The gate has to be measured, not chosen**: `amabie setup`
  already runs the plan once as a smoke test, so it already knows the plan's duration and can install
  mid-task feedback only when that duration makes per-edit runs defensible.
- **It must not become a verdict.** The hook would run the project's own declared command, in the user's
  ordinary environment — not the sealed plan under its sanitized env and pre-gates. That is the project's
  output, exactly as in the confined design, and it must be labelled as such: it cannot mint a `PASS`, it
  does not touch `NO PROOF, NO DONE`, and the completion gate remains the only thing that decides.
- **It is unmeasured as a saving.** The confined result is evidence that this CLASS of move pays, not
  evidence about this instance; the everyday fixtures would have to show it, and the one permitted pilot is
  spent.

**Recommendation, not a build.** The lever is real and now reachable; the gate that makes it safe is
already computable at setup time. But shipping it unmeasured would repeat the mistake this audit keeps
catching, and shipping it *by default* on a suite-duration guess repeats the mistake twice. Recorded here
so the next step is a decision rather than a rediscovery.

**AND THEN IT WAS BOUNDED, FOR FREE, WHICH CLOSES IT.** Before building anything, the recorded trials answer
the question the build was for: how much self-checking is there on the everyday path to remove? Every trial
records the commands the model ran itself (`stream.commands.checks`, from `tooling/benchmark/stream.mjs`).
The first version of this table was written from a misread grep — token totals mistaken for turn counts —
and the probe that now pins it (`v13-posttool-feedback.mjs`, D1/D2) printed the real numbers:

| guarded (everyday) fixture | turns | model-run checks | Amabie commands |
|---|---|---|---|
| add-validation | 14 | 2 | **0** |
| bound-requirements | 10 | 1 | **0** |
| bug-sum | 6 | 1 | **0** |
| cross-file-refactor | 19 | 2 | **0** |
| regression-guard | 12 | 2 | **0** |
| stateful-replay | 17 | 1 | **0** |
| **total** | **78** | **9** | **0** |

**The everyday agent already barely checks anything — 9 self-run checks across 78 turns, 11.5 %.** So
mid-task feedback has a ceiling of roughly **11.5 %** of the everyday path's turns, and that ceiling is not
a saving: it assumes every one of those checks was redundant, when some are the agent legitimately testing
its own work. Even at the ceiling, 92.7 % becomes about 82 %, not 75 %. **The mid-task lever is therefore
real, reachable, and still too small to matter for this criterion.** Building it would have been a feature
justified by a mechanism rather than by a measurement — the same error this audit has now caught six times,
avoided here by looking at data that was already on disk.

**That closes the everyday path honestly, and the conclusion is uncomfortable rather than convenient: the
everyday shape cannot be materially cheaper than plain, because it does the same work.** Plain runs ~2
checks of its own (measured by the token ledger) and so does the guarded arm; Amabie adds a completion gate
and removes almost nothing, which is exactly why the ratio sits at 92.7 % and why every route to 75 % on
this shape has failed. What the everyday path buys is not fewer tokens — it is that a green suite which
cannot discriminate the change stops being accepted as done. That is the claim the README makes and it is
the claim the numbers support.

**One further observation falls out of the same table, and it belongs with the OPEN finding about the
standing payload:** `amabie` commands are **0** in all six everyday records — the agent never called a
Amabie tool, in any of them. That is consistent with `run-trial.mjs` passing `--strict-mcp-config` with no
`--mcp-config`, so the measured arms had no MCP server at all. It is a second, independent confirmation
that the 92.7 % figure is the Stop-hook-only shape — and it means the token cost of the tool surface is
**unmeasured rather than zero**, which D2 now fails on if that ever changes.

| basis | plain | amabie | ratio |
|---|---|---|---|
| medians (long = 288,942 vs 208,252) | 405,299 | 386,065 | **95.3 %** |

and the short cells have no unflagged counterpart at all. No default change is justified by that, and the
flag stays opt-in.

### THE DOCS NOW DESCRIBE THE SIMPLER PRODUCT — and the one that mattered was the agent's

The last item of the v1.3 objective is "docs rewritten around the simpler product", deliberately last so
the docs describe a product that already exists. The README was rewritten in slice 7. Checking the rest
turned up the document that actually changes behaviour: **`AGENTS.md`, the file every coding agent reads
in a repository, still opened its usage section with the `amabie work` → `amabie finish` ceremony.**

That is not a stale sentence, it is an active cost. Over the recorded corpus the ceremony ran at
**177.8 %** of a plain run where the everyday shape ran at **92.7 %**, with identical correctness and no
false done in either. Every agent that read `AGENTS.md` and followed it was being pointed at the shape
that costs nearly twice as much, while the audit's own headline recommended the other one. The section now
leads with the everyday path — `setup --yes` once, then work normally, the hook verifies — and presents the
candidate path second, labelled as the expert surface, with its measured cost attached.

The other three agent-facing surfaces were already correct and were verified rather than assumed:
`amabie mcp`'s instructions frame the candidate tools conditionally ("for work that must be isolated"),
the advisory block `amabie agents install codex` writes into other projects' `AGENTS.md` leads with the
everyday path, and the README has shown the everyday path first since slice 7, with the ceremony confined
to a clearly-labelled Expert mode that already carries the 177.8 % figure.

`tooling/probes/v13-doc-first-path.mjs` **pins the order and the honesty**, because both are load-bearing
and both are one careless edit away from reversing: for each user-facing doc it asserts that the first

the automatic-verification half that produced the cheaper shape, and the reliability half this repository
measured must stay (the variant that forbade self-verification outright produced a false done *and* a false
green).

### THE ONE NAMED REQUIREMENT THAT IS DELIBERATELY NOT BUILT — and the guarantee it was for, measured

The v1.3 objective asks the everyday path for an **invisible candidate/promotion lifecycle**, and this
audit records as an OPEN finding that the everyday path neither isolates nor promotes: no candidate, no
frozen task authority. That finding is real. **The recommendation is to leave it unbuilt**, for two
reasons, and then to measure the thing it was actually for.

**It would be a second implementation of gates.** The PROPOSED EXPERT WORKFLOW above sets the rule:
everyday mode is "a *presentation and orchestration* layer over them — it must never be a second
implementation of a gate, because two implementations is two places for a gate to be weakened." A
checkpoint-time candidate would re-derive isolation, base comparison and promotion inside the everyday
path, beside the ones `work`/`finish` already own. The failure mode is not hypothetical: this repository's
own history is a list of gates that were weakened in one place while another still looked right.

**It costs turns for a property that is already guaranteed.** The ceremony is measured at **177.8 %** of a
plain run against **92.7 %** for the everyday shape, with identical correctness. Paying that on every
ordinary turn — the shape the whole release exists to make cheap — to buy a lifecycle whose guarantees are
already provided would invert the priority order the brief sets (trust, correctness, bug resistance,
simplicity, **then** tokens).

**So what was the lifecycle FOR?** Not for the machinery: for the guarantee that *nothing is blessed on
the strength of a record*. On the everyday path that guarantee comes from somewhere stronger than a
candidate — the verdict is **never read back at all**. `apps/cli/src/onboarding.ts` states the design
("doctor's READY is always earned in the invocation that prints it… a stored checkpoint can never produce
READY on its own"), and the evidence bundles record candidate identity, exact argv, cwd, runtime identity,
env overrides, raw stdout/stderr with full sha256, exit code and independently derived observation counts.

That is a claim in a comment, and this repository's doctrine is that a claim is not evidence. So
`tooling/probes/v13-verified-bytes.mjs` attacks it with the most convincing forgery it can construct: a
checkpoint record whose shape is byte-identical to what a real green run writes
(`{at: <now>, status: "pass", failed: [], source: "checkpoint"}`) planted on a repository whose checks
**FAIL**. Measured, on the real completion path:

| | measured |
|---|---|
| a green tree | **allowed** — the control, so "blocked" below cannot be an always-blocking gate |
| breaking the code, with a green record still on disk | **blocked** — the verdict follows the bytes |
| a forged PASS record on the failing bytes | **still blocked** — no record can produce a pass |
| `doctor` with the forgery present | **not READY** |
| repairing the code, forgery still on disk | **allowed again** — so the block was the bytes, not the file |
| `status` describing the stored record | labels it **"NOT a claim about now"** |

The two controls are what make this worth recording: the second one runs *after* the forgery is planted,
so a pass cannot be explained by the forged file merely poisoning the repository.

**Conclusion, stated so it is not mistaken for a gap left open:** the user is exposed to no candidate or
promotion ceremony — the "invisible" half holds in the only sense that helps them — and no unverified
bytes are ever blessed, which is measured rather than argued. Building the literal lifecycle would add a
second gate implementation and roughly double the everyday token cost to re-provide a guarantee that the
everyday path already has by not trusting records at all.

### THE LAST INTEGRATION OBSTACLE IS A SCOPE, NOT A GATE — measured

MEASURED UPDATE 3 concluded that Claude Code's `⏸ Pending approval` step cannot be closed from any
settings file Amabie writes: four candidate forms, two independent views, byte-identical output. That
conclusion was about *satisfying* the gate. It never asked whether the gate could be **avoided**, and the
answer changes what v1.3 can honestly claim about integration.

`claude mcp add` takes `-s, --scope <local|user|project>`, and the **default is `local`, not `project`** —
but `amabie setup` registers at project scope, which is why the approval step exists at all.
`tooling/probes/v13-mcp-scope.mjs` measures what each scope produces, with a minimal real MCP server in a
throwaway repository:

| scope | where the entry lives | Claude Code reports |
|---|---|---|
| `project` | `.mcp.json` in the repository | **`pending-approval`** |
| `local` | the user's own `~/.claude.json`, keyed by project path | **`connected`** |

**The asymmetry is correct, and it is why this is a scope decision rather than a workaround.** A
project-scoped server arrives from a *file in the repository*: a clone, a branch or a pull request can put
it there without the user doing anything, so holding it for consent is the harness protecting the user, and
Amabie must not try to defeat it. A local-scoped server is the user's own private configuration for this
project; nobody else can write it, so there is nothing to consent to — and the harness applies no gate.

**The trade-off is real and is a product decision, not an obvious win.** Project scope gives a teammate the
tools from a clone (and each of them must then approve it once). Local scope gives a teammate nothing until
they run `amabie setup --yes` themselves — which is already the documented model, and which also stops
`setup` writing a second file into the user's repository at all (the file that caused the `--reseal`
regression and the `isAmabieOwnArtifact` work in the second slice). Against that: it means Amabie writes
into a configuration file **outside** the repository, so it must do so only through `claude mcp add` /
`claude mcp remove` — never by parsing or writing `~/.claude.json` itself, because the harness owns that
format — and it must report honestly when the harness CLI is not available to undo it.

**So the honest state of the integration claim is:** the *completion gate* has been genuinely seamless
since the Stop hook — no approval, no user action after `setup` — and the *tool surface* requires one
approval **only because Amabie chose project scope**. That is now a measured choice with a measured
alternative, not an unavoidable harness limitation. Recorded before changing it: the scope `setup` uses is
a behavioural change for teams, and it is worth making deliberately rather than as a side effect.

**Honest position: the first slice does not reduce code, and the plan's complexity reduction is not yet
earned.** What the slice does is remove a *dead end* and a *false claim*; what it adds is ~90 lines of
product code and no new subsystem.

What the plan must actually buy, in order:

1. **Everyday surface: 3 commands → 1.** `work` and `finish` move behind the agent's tool surface; the
   human types `setup` once. This is a *deletion* of user-facing surface, not an addition.
2. **Human decisions per task: 1 → 0** for tasks whose prose names their kind (measured: 3 of 4
   wordings now complete with no declaration at all; the fourth refuses before spending anything).
3. **Vocabulary: MEASURED, and it is already most of the way there — so this item is closed rather
   than rewritten.** `tooling/probes/v13-everyday-vocabulary.mjs` counts the internals the ordinary
   path speaks: **13 occurrences of 5 distinct terms** — `status` 7 (`sealed` ×2, `seal` ×2,

   is the one the AGENT reads, and apart from those five words it is plain, actionable English:

4. **No new subsystem.** The engine stays one engine: the verification core, the candidate/promotion

   `result`/`doctor`/`work`/`finish`.

**Explicitly rejected as complexity for too little benefit:** a second lifecycle for Cursor; a
per-agent architecture; auto-binding heuristics; any "smarter" default that invents an obligation.

## SECURITY RISKS

**Introduced by the first slice, and why each is bounded:**

| Change | Risk | Bound |
|---|---|---|
| Widened `inferTaskKinds` | A mislabel adds a duty the change cannot discharge → a **false block** | Kinds are a **union**: a mislabel can only *add* obligations, never remove one. The words added **assert brokenness** (`wrong`, `incorrect`, `failing`, `misbehav*`, "does not work") rather than name a topic; a test pins that `add error handling to the parser` still infers **nothing**. Direction of error is toward more verification, never less. |
| `work` refuses when no authority is frozen | Could refuse a task that would have completed | It cannot: the frozen kind set is exactly the authority `candidate.ts:602-609` requires, so such a candidate is **always** refused at `finish`. The gate moves discovery from after the spend to before it — 0 candidates opened, 0 worker launches, 0 tokens. |
| `agents` reports wiring, not detection | Could under-report protection | It reports the same fact `status` and `readOnlyProblems` already compute from the config and settings files. Strictly *less* claiming; the failure mode is conservatism. |
| `finish` names the real recovery for `task-authority` | None | Presentation only; no gate, verdict, exit code or envelope changes. |

**Preserved, verified by the existing batteries:** the worker cannot self-bind, cannot seal its own
authority, has no unrestricted fallback, and cannot promote itself; verification authority stays
frozen at isolation; `HARDENED` remains reachable only from a measured deployment. The escape battery,
the alias-lifecycle audit, the production attack battery and the pre-bound end-to-end workflow are all
re-run against the changed bytes before any claim — see the verification record at the end of this
document.

**Residual risks that are NOT fixed and must not be implied away:**

1. **An agent with shell access can re-seal.** `amabie setup` has no TTY gate (only `accept` does), so
   an agent can clear a drift block by re-running setup. The discrimination obligation still blocks a
   weakened suite, but the drift *gate* is not agent-proof. Open, documented, unchanged by this slice.
2. **On the default path the agent's writes are unconfined, and the change is never isolated.** The
   *verdict* risk is covered — a change the sealed checks cannot discriminate is blocked (measured,
   section F2) — so this is a lifecycle gap, not an acceptance hole. It is nonetheless the reason the
   everyday path cannot promise "the bytes that passed are the bytes you have".
3. **The model CLI process is not confined**; only its tool calls cross the boundary, and the existing
   probe measures the *advertised* tool list rather than the CLI's inability to act natively.
4. **Same-UID forgery, no network egress control and no filesystem jail** remain the documented LOCAL
   ceiling. Nothing in this audit narrows or widens them.

## FIRST IMPLEMENTATION SLICE

**"The ordinary path either works, or says so before spending anything — and Amabie never claims
protection it does not have."**

Chosen because it is the smallest change that (a) fixes a measured trust defect, (b) removes the
dead end in the exact path v1.3 must make work, and (c) adds no subsystem. Four changes, three files:

1. **`apps/cli/src/onboarding.ts` — `inferTaskKinds`.** Added the ordinary ways a developer *asserts*
   brokenness. Justified by this repository's own benchmark fixture: `bug-sum`'s task statement
   ("*…a test suite (npm test) that is currently failing.*") previously inferred **nothing**, so the
   corpus's most ordinary task was a guaranteed dead end.
2. **`apps/cli/src/orchestrate.ts` — `cmdWork`.** Refuses, before isolation, when the registered task
   freezes no authority: prints `CANNOT BE JUDGED`, opens no candidate, launches no worker, and names
   the one thing the human must supply.
3. **`apps/cli/src/onboarding.ts` — `agentCapability` + `gatingHookInstalled` + `cmdAgents`.** "Detected"
   and "protected" are now different answers; `hooked` means the hook is installed in *this*
   repository, and the verdict is decided by wiring. `apps/cli/src/protocol.ts`'s doc comment was
   corrected to match.
4. **`apps/cli/src/candidate.ts` — the refusal's `next:` lines.** `task-authority` is no longer
   classified as worker-closable, and its recovery (re-register with a kind, open a fresh candidate)
   is stated plainly first.

**Measured result** (`node tooling/probes/v13-journey-baseline.mjs`, **15/15 observations held**, exit 0,
1 recorded open finding):

| fixture | before | after |
|---|---|---|
| intent matching no keyword | `work` exit 0 → candidate opened → correct fix refused at `finish` (exit 2) | `work` exit 2, **candidate not opened**, refusal names `--kind` |
| same intent + `--kind bugfix` | completed | completed (unchanged) |
| intent containing "fix" | completed | completed (unchanged) |
| **`bug-sum`'s own task statement** | **nothing inferred → dead end** | `bugfix` inferred → **completes, exit 0, bytes promoted** |
| `.claude/` present, no hook | `agents` → `CONNECTED`, exit 0 | `agents` → `NEEDS ATTENTION`, `hook NOT installed here`, exit 2 — **agrees with `status`** |

The benchmark harness's own classification is unaffected: `v12-workflow-preflight.mjs` still reports
`bug-sum` as `A-executable` — and that label is now *true*, where before it described a candidate that
`finish` would have refused.

**The `OPEN` finding this slice leaves behind** is the everyday path's missing lifecycle — no
isolation and no frozen task authority (section F, and the correction above). It is recorded, not
asserted, and it is deliberately not a red: it is a gap in *when* Amabie acts, not in what it accepts,
and the probe proves the acceptance question is already closed.

## SECOND SLICE — the agent can ASK, instead of guessing

**"`setup` registers Amabie's tools, so the agent stops running its own verification campaign."**

Chosen because the correction above moved the target: the acceptance question is already closed on the
everyday path, but the gate only speaks at the **end**. So the agent cannot ask *"am I done?"*, and it
does the only thing it can — it verifies itself. Measured on the long fixture: **~36 of 57 confined
execs were the model re-running its own checks**, plus a self-authored fuzz/mutation rig written as
whole-file payloads (58,587 B). That behaviour is rational, and it is ~70 % of that arm's token cost.
Removing the *motive* is the lever; forbidding the behaviour is contradicted by this repository's own
measurements (the arm told not to verify produced a false done and a false green).

**What was already there.** `amabie mcp` — a stdio MCP server that exposes exactly six thin argv
templates over commands the CLI already had (`result`, `status`, `agents`, `doctor`, `work`, `finish`),
deliberately **not** exposing `accept` (that is a human act in a terminal). It grants no authority: it
can only *request* operations, and every one of them is judged by the same gates. The missing piece was
that a user had to discover and configure an MCP client by hand.

**What this slice adds** — `apps/cli/src/onboarding.ts`: `installMcpServer`, `hasMcpEntry`,
`pruneOwnedMcp`, wired into `setup` beside the Stop hook, with the same discipline that file already
had for `settings.json`: parse before writing, refuse to write through a link, back up the previous
bytes, prune only entries this installation wrote, write atomically, and record what was touched so
`uninstall` can undo exactly that. Ownership is the **argv signature**, never the key name.

**The regression that mattered most** is not the server: it is that `setup` now writes a second file
into the user's repository. `isAmabieOwnArtifact` had to learn about `.mcp.json`, or the freshly written
file would count as *the change*, the sealed checks would be green on the base too, and **every
repository would report NOT PROVEN the moment it was wired** — the verifier's own file mistaken for the
author's work. Section G3 of the probe asserts that this does not happen.

**Measured result** (`tooling/probes/v13-journey-baseline.mjs` §G, **24/24 observations held**, exit 0):

| property | measured |
|---|---|
| G1 | `setup` writes one entry running this Amabie as an MCP server |
| G2 | a stranger's server entry is preserved byte-for-byte |
| G3 | **the newly written file does not make the repo look changed** — `status` stays CONNECTED |
| G4 | the completion gate still allows a wired repo with no change |
| G5 | re-running `setup` is byte-identical (324 bytes before and after) |
| G6 | a foreign server under our key is **refused, not replaced**, and the file is unchanged |
| G7 | a real `initialize` + `tools/list` handshake returns `serverInfo.name = amabie` and exactly 6 tools |
| G8 | `accept` is not among them |
| G9 | `uninstall` removes exactly our entry and keeps the stranger's |

Plus `apps/cli/test/mcp-wiring.test.ts` (9 cases) so the merge/refuse/prune semantics are protected by
`npm test`. **That test caught a real bug before it shipped:** pruning our only entry deletes the
`mcpServers` object itself, so a reference taken before the prune wrote the new entry into a detached
object — a re-run produced a file with *no servers at all*. The fix re-acquires the map after pruning.

**And the battery caught a second, worse one — this is the part worth reading.** Teaching `setup` to
write a third file broke `amabie bind --reseal` for every user: `--reseal` commits the declaration
alone and *refuses when any other path is dirty*, and the freshly written `.mcp.json` counted as
"another change". The operator would have been told their working tree held changes Amabie itself had
just made, with no fix available. `verify:productization` reported it precisely —
**`FAIL 1.2 REQUIREMENT UNBOUND gate (no worker is handed a duty it cannot close)`, 82 of 83 steps
green** — and nothing else in the suite noticed.

The repair is structural, not a patch: the excluded set was a hard-coded settings path, and is now
read from `cfg.touched` — the same list `setup` records, excludes from its baseline, and `uninstall`
prunes — so it stays correct as the managed surface grows. The probe that caught it was making the
same mistake from the other side (a hard-coded list of "Amabie's own paths"), so it now derives the
set from the config too: **a probe that must be edited whenever the product changes is a probe that
will eventually be edited in the wrong direction.** The property that actually matters — that
`--reseal` sweeps no unrelated work into the commit — is asserted separately, on the commit's own
contents, and was never in question.

**Honest limits of this slice:**

- **It is not "seamless" yet, and must not be described as such.** Claude Code's own consent gate for
  project-scoped MCP servers still applies; Amabie writes the entry, the harness decides whether to
  honour it. This removes a *configuration* step, not the harness's approval.
- **It does not confine anything.** The agent's native tools remain available and remain the executor;
  the tools added are Amabie's read/verify/lifecycle operations.
- **The token win is projected, not measured.** The mechanism is measured (the self-verification
  campaign is real and costs ~70 % of that arm); whether an agent *uses* the tool instead of running
  tests is exactly the "model tool choice" question that v1.2's optional-batch experiment got wrong by
  assuming. It must be measured, not asserted.
- **`setup`'s output now names the file it wrote** — a file Amabie adds to someone's repository must
  never appear unexplained.
