## EVERYDAY UX

`amabie setup --yes` once per repository; then the agent is used normally and Amabie speaks only
when it has something to say. **No ordinary requirement to know or run `task`, `bind`, `work`,
`finish`, `candidate` or any proof vocabulary** — measured by `tooling/probes/v13-doc-first-path.mjs`
and `tooling/probes/v13-everyday-vocabulary.mjs` (a ratchet on the words a user must decode), both
PASS. `AGENTS.md`, `README.md` and `docs/TROUBLESHOOTING.md` all lead with this path. The everyday
path is unchanged in behaviour by v1.4: the same `setup` → `Stop` hook → `checkpoint` chain, with
**no new authority** anywhere.

**Not re-measured in v1.4, and deliberately so.** Running the model benchmark again would not change
the classification, and the mandate forbids spending on the metric for its own sake. What v1.4
*changed* is the honesty of the published claim: the 92.7 % was measured with the agent launched
**without** the MCP server, so it omits a standing cost paid every turn — **5,726 B/turn**
(1,475 B instructions + 4,251 B tool definitions), of which **1,923 B (33.6 %) is expert-only
ceremony**. `README.md` now says plainly that the real everyday footprint is **somewhat worse** than
92.7 %, not better.

## TOKEN TARGET <= 75 %: **NO**

**Not reached, not claimed, and not reachable by the means available.** Two independent routes to a
lower number were already measured before this release and both are bounded: removing the MCP
standing payload entirely returns **≈ 2 points**, and eliminating the repair turn entirely is
**≈ 5.9 %** — described in the v1.3 audit as "an upper bound on an impossible act". Their
impossible sum lands at **≈ 85 %**, not 75 %. Reaching 75 % would require the agent to do
materially less work, i.e. removing verification, which the priority order forbids
(**"Do not trade the gate for the number"**). The remaining sliver — not advertising the two
expert-only MCP tools to everyday users — was **rejected as NOT WORTH COMPLEXITY**: it is worth
roughly 1,923 B of 5,726 B, about **2 % of the everyday arm**, and it would make the advertised tool
surface depend on repository state, which is harder to reason about than it is worth.

## SECOND AGENT

**OpenAI Codex CLI — SOLVED AND MEASURED.** `amabie setup` writes a `Stop` hook into
`.codex/hooks.json` running the same `checkpoint` (one implementation, no fork, no new authority).
A **real `codex exec` session** (`codex-cli 0.154.0`) executed the hook **twice**: once blocking
(`{"decision":"block","reason":…}` on stdout, exit 0) and once with `stop_hook_active: true`
allowing — and the harness **continued the turn** on Amabie's reason.
`tooling/probes/v14-codex-stop-hook.mjs`: 15/15 observations, exit 0, registered in
`verify:productization` and **PASS**. `agents.ts` therefore reports `gating: true,
gatingMeasured: true` — justified by an observation, not by documentation.

Two measured caveats ship on the capability row, not in a footnote: **Codex runs a project hook only
after a one-time review and trust (`/hooks`), so an untrusted hook is written and gates nothing**;
and Codex has **two** trust layers (a project `.codex/` layer that is not loaded at all until the
*project* is trusted, and the per-hook record that `--dangerously-bypass-hook-trust` can skip). Also
measured: **Codex rejects an entire `hooks.json` carrying an unknown top-level field**, so Amabie's
writer emits only `hooks` and preserves everything else. The probe asserts project trust inside an
**isolated `CODEX_HOME`** and this audit confirms the operator's real `~/.codex/config.toml` is
byte-unchanged (6,348 bytes, zero mentions of the probe's diagnostics).

## LOW-EVIDENCE REPOS

**Improved, and the authority boundary did not move.** Three concrete failures were found and fixed
as **disclosure**, with **no new discovery and no new authority**:
1. When the universal adapter finds two equally-anchored checks it deliberately refuses to choose
   and returns one clarification line — `setup` used to **discard that line** and print a generic
   refusal. It is now printed before the verdict.
2. Both no-check refusals listed only Node/Python/Rust/Go and so **understated what Amabie reads**;
   they now name the universal contract (Makefile / Taskfile / Justfile, a shipped `gradlew` or
   `mvnw`, configured CMake/Meson/Zig/Swift/Elixir/Crystal/Rake/Composer/PHPUnit, or a check the
   project's CI already runs).
3. Root cause of both: **not missing discovery but missing disclosure** — the engine knew more than
   it told the user.

**CHECK DISCOVERY may get better; SEMANTIC AUTHORITY did not move at all.** Binding remains an
operator act in `package.json` `amabie.proofs` (64-hex digest keys, values that must name an
in-plan script or the seal **throws**); `amabie work` still refuses with `REQUIREMENT UNBOUND`
before opening any candidate; the checkpoint still refuses to certify before executing when
authority drifted. All of this is covered by the battery's authority and trust-boundary steps,
which PASS.

## BEGINNER UX

**Improved on the everyday path, without weakening meaning.** Translated: `setup`'s trust-store
refusal and its seal refusal (previously `REFUSED — <raw internal throw>`), `amabie result`'s
"no sealed checks, no proof, no result", and the last-resort handler (previously a bare
`ERROR: <internal text>`, which now states that this is a **defect in Amabie**, that the run
**verified nothing**, and how to report it). Every message keeps its **exact exit code**, its
factual content and its actionable next step; the internal detail moved behind the `--verbose` flag
that already existed.

**Two boundaries were respected deliberately.** Where a test or an operator workflow *parses* the
text — `unbound: <digest>` and `available to bind:` in `setup` output, consumed by
`tooling/probes/v12-requirement-unbound.mjs` — the lines were left **byte-exact**: a message an
operator workflow reads is a contract, not prose. And the `NOT PROVEN` / `NO sealed proof` verdict
wording was left alone because it is **pinned by tests and by the acceptance probes**; those strings
already say what happened and what to do, and the mandate forbids weakening a gate for cosmetics.

## KNOWN LIMITATIONS

Unchanged from v1.3 except where noted:

- LOCAL is not an OS boundary; `HARDENED` is unreachable without a measured deployment.
- A declared binding is **declared proof coverage, not semantic truth**.
- Everyday edits are not confined.
- One block per stop; one harness-owned MCP approval at project scope (avoidable at local scope).
- Cursor: UNMEASURED, no protection claimed (**now with a procedure**, still no host).
- Confined coverage **5 of 20** fixtures; the other 15 refuse before model execution.
- `AMABIE_CONFINED_CHECK` stays opt-in, with mixed evidence in both directions.
- No demonstrated correctness advantage (plain was already 36/36).
- **NEW (v1.4):** Codex gating requires a one-time hook-trust review (`/hooks`) and, separately, a
  **trusted project** — the `.codex/` layer is not loaded at all otherwise. Until both hold, the
  hook is written and **gates nothing**.
- **NEW (v1.4):** the everyday token claim **excludes** a 5,726 B/turn standing payload, so the real
  footprint is somewhat worse than 92.7 %.
- **NEW (v1.4):** the GitHub-hosted Windows CI leg stalls on a handful of pipeline tests and is
  classified a host limitation, with its measured profile documented in the workflow.
