## Authority repair implemented

The production broker now refuses candidate proposals that create, replace,
modify or remove proof-binding declarations in either `package.json` or
`amabie.project.json`, including Windows case aliases. Implementation edits
preserving those declarations still reach independent verification.

The operator still owns binding/sealing. The real production probe performs
`bind --reseal`, verifies the frozen binding, enrolls the deployment, and then
executes the attacks from its actual restricted caller. A legitimate candidate
is reviewed, promoted by the broker, and re-read successfully afterward.

## Production tool/transport path implemented, not yet end-to-end complete

New product commands:

```
amabie provider worker-tools <store> <work>
amabie provider model-transport <store> <work> <prompt-file> <model> <absolute-claude-executable>
```

The trusted transport disables Claude native tools, skills, hooks, project/local
settings discovery and Chrome integration. Its only advertised model tool is
`mcp__amabie_confined__implement`. Each tool request is staged under the existing
exclusive caller lock and runs inside the existing restricted, low-integrity,
zero-capability AppContainer. Native token/exit observations are checked before
tool output is returned. Output is untrusted context, never verification evidence.
There is no host-side implementation fallback. Unknown MCP tools are rejected.

API credentials remain in the model transport. The MCP bridge removes them from
its own configured environment; the native runner supplies the executor's fresh,
secret-free environment. Both caller and verifier receive read/execute-only
access to the deployment's existing copied Node/npm runtime, not write access
or access to adjacent broker keys. Runtime packaging includes the new executor.

`v12-model-transport.mjs` uses the **real installed Claude CLI**, the real product
commands and the real AppContainer, with a deterministic local fake model server.
It does not call a paid model or supply real API credentials. Its dummy usage
events are transport-test data, not Qwen benchmark measurements.

## Exact technical blocker

Installed Git: `2.55.0.windows.3`. Inside the measured AppContainer:

- `git --version` succeeds.
- `git init` fails, exit 128.
- `git -C <work> init` fails, exit 128.
- Explicit `--git-dir=<work>/.git --work-tree=<work> init` fails, exit 128.

All three mutations report:

```
fatal: unable to get current working directory: Permission denied
```

Ordinary file writes, cmd execution and child Node execution succeed in the same
workspace. This is a required capability failure, not an attack blocked for
the right reason. The probe retains its failing Git assertion and exits 1.
The unrestricted Git init positive control succeeds in that exact workspace;
it is run after recording the confined failure and cannot satisfy the assertion.

Source investigation: Git's
[`mingw_getcwd`](https://raw.githubusercontent.com/git-for-windows/git/v2.55.0.windows.3/compat/mingw.c)
uses Windows final-path and long-path resolution. A
[matching AppContainer issue](https://github.com/microsoft/mxc/issues/694)
reports DOS-volume final-path access failing and describes global object-manager
ACL changes. This supports the diagnosis; this audit has not directly traced
each failing Windows API call. No global ACL changes, extra network capabilities,
unrestricted Git fallback, or external Git replacement were applied.

The next repair needs a compatible confined Git runtime/path-resolution solution
and the same security battery afterward. No `gcc`, `clang` or `cl` was found on
PATH during this session; that is not a claim that no compiler exists elsewhere.
