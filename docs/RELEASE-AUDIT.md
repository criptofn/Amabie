# Amabie 2.0 release audit — READY FOR FINAL APPROVAL

What this repo does: Amabie runs declared project checks, compares changes with sealed baselines and retains evidence. Its classifier is deterministic. Expected load is one independent developer, with potentially hostile coding-agent edits under the same user identity; LOCAL is not an OS sandbox.

## Open historical containment incident — not closed by this mission

The public [Canary v1.5.0 release notes](https://github.com/criptofn/Canary/releases/tag/v1.5.0), `docs/AUDIT-KIT-1.5.md` section 7.0 and `docs/CLAIM-EVIDENCE-MATRIX-1.5.md` record one hosted Windows failure: the live-parent descendant test reported that the sweep killed PID 7564 but omitted expected PID 2144 after 35980 ms. Four later hosted greens and 14 local attempts did not explain it. The release explicitly kept its cause **OPEN / UNEXPLAINED / NOT FIXED**; the failure diagnostic did not run in successful repetitions.

The current reviewed baseline contains later, relevant product changes:

- Commit `2fb4bd050ec9be4b396a358862afecbba42c52af` (2026-10-08) unions descendants from both pre-kill CIM snapshots and traverses the final snapshot, so a newly visible surviving descendant refuses the sweep. Its deterministic Windows regressions cover first-snapshot omission and final-snapshot survivors while preserving older reused-PID processes.
- Commit `16624d5` restricts each CIM snapshot to process identity fields to reduce observation cost. It is not an isolation guarantee.
- Current Windows full tests pass the live-child case and both snapshot regressions. The productization log also records **12/12 harmless cleanup stress attempts**, six idle and six under CPU load, leaving each root alive and terminating its expected descendant. These are local observations, not a reproduction of the original hosted host.

These mechanism repairs cover plausible omission shapes, but **no recorded diagnostic establishes which shape caused the original failure**. The new everyday supervisor fix merely starts using the shared sweep; it does not establish closure of this historical central-sweep incident. This mission has not changed the shared sweep algorithm relative to the reviewed renamed baseline; its differences are branding/comments.

Release judgment: retain this as an **unresolved, environment-specific reliability investigation with a possible high integrity consequence**. A current run reporting successful containment while an independently observed descendant remains alive would be a confirmed release blocker. No such current reproduction is established by the available tests. Current passing gates support only documented LOCAL, bounded best-effort cleanup; they do not justify universal no-survivor claims, historical closure, HARDENED activation or an assertion that hostile code cannot escape. The final release report and known-limitations page must retain this incident. Reproducing the same hosted failure with its identity/CIM diagnostic is still unverified; more green local repetitions cannot supply that explanation.

## Residual limits and risk interpretation

The confirmed scope, everyday-supervisor and canonical-pin defects have passing regression evidence. The unsupported-Node support-contract repair is staged and verified in the isolated native Linux copy: an early startup refusal precedes command dispatch and metrics writes, with `UNSUPPORTED`/exit 2 and a single JSON envelope when requested. Native Node 22.23.3 full suite: **1360 tests, 1354 passed, 0 failed, 6 host-bound skipped**, duration **68991.974698 ms** (`node-runtime-linux-tests-r2.log`). Six new runtime regressions cover setup, JSON doctor, checkpoint, MCP, help, no project/trust/metrics state writes and supported-runtime help/version. The actual official Node 20.20.2 Linux archive was SHA256-verified (`df770b2a6f130ed8627c9782c988fda9669fa23898329a61a871e32f965e007d`) before executing the isolated candidate package: all five unsupported invocations refused with exit 2 and clear remediation, while supported Node 22 package help succeeded. Evidence and clean patch are under `amabie-web/artifacts/release/node-runtime-fix/`; that Linux-only candidate tarball has SHA256 `a5f82042a0a71e4657d0ee14dfc944b0a87d5269f59de13dd473d653042ea566` and is not the final release artifact. The parent must apply the patch after the active Windows battery, rebuild the final package, and repeat its affected gates before marking the original Windows unsupported-runtime defect resolved. No additional current critical/high security reproduction was found in the tested scope, but the historical containment investigation above remains explicitly open. This scoped conclusion is not a claim that the complete release mission has passed or that unknown vulnerabilities cannot exist.

- **LOCAL is not an OS sandbox.** Project checks run as the developer's user; hostile code can read same-user filesystem data, use the network and replace the entire trust store, including keys and history. Ed25519 protects records against edits relative to the retained issuer, not full same-user issuer replacement.
- **Authority records and evidence bundles are different.** The trust store signs authority records. Everyday `verification.json` plus its self-hash is tamper-evidence, not a signed independent attestation; that bundle is not read back to decide completion. Evidence persistence is best effort and can fail even when a live check completes; the final rehearsal must confirm retained artifacts.
- **Containment is bounded user-space cleanup.** It is not a cgroup, Job Object or filesystem jail. A POSIX descendant that leaves both session and lineage via daemonization is outside the documented reach. Root/ancestor replacement during path resolution and later filesystem writes remain inside the same-user ceiling.
- **Checks define proof scope.** Declared commands and operator-selected bindings must measure the intended behavior. Equal passing results can remain NOT PROVEN; discriminating tests are evidence within their coverage, not semantic correctness guarantees.
- **Current observations are host-specific.** Windows and Linux evidence does not establish macOS runtime parity or privileged provider activation. The previously absent pytest/POSIX cases now have separate executed evidence; unavailable HARDENED activation must stay unavailable in marketing.
