# Prompt-to-Evidence V1 (experimental)

Status: **opt-in prototype for coding tasks**. This feature is not part of the stable Amabie 2.0 interface and must not be described as Universal Agent Assurance. The implementation request's Section 3 is strategic Phase 2; numbered work-plan sections do not change the product phase definitions. See [NORTH_STAR.md](NORTH_STAR.md) for the strategic phases and the Phase 3 acceptance gate.

## What the prototype verifies

The request envelope contains the original task text, a task-domain identifier, and each declared requirement with a source reference, clarity state, and one or more deterministic criteria. Amabie checks that the task-domain identifier, task digest, and multiset of requirement digests exactly match the task registered locally. The task domain is part of the correction-scope fingerprint, so a correction cannot silently switch verifier domains. It also recomputes lexical source coverage: every non-whitespace character in the original goal must map exactly once to a goal-linked requirement, and each quoted span must match that requirement text (an explicit list marker may be removed). A missing span, overlap, or paraphrase that does not match its quote keeps the overall result `NOT PROVEN`; it cannot be repaired by changing code, so the correction loop stops for operator review. Stable requirement and criterion IDs are derived from the content and source reference; the agent cannot choose an easier ID or silently omit a registered requirement.

A verifier adapter collects facts and artifact references. It does not return a verdict. The shared core applies a small deterministic JSON-Pointer equality rule, checks evidence type, adapter identity, run identity, scope and a content digest, then assigns `met`, `unmet`, `unproven`, or `blocked` per requirement. Missing bindings and missing facts remain `unproven`; execution failures are `blocked`; contradictory measured facts are `unmet`. An `unclear` requirement cannot become `met` even when a check is green. An empty requirement set, incomplete lexical prompt coverage, a source quotation that does not match its requirement text, or a requirement without machine-verifiable criteria is `NOT PROVEN`, never a vacuous pass. Source coverage proves only that the prompt text was mapped; it does not prove the semantic split or that the selected checks express the user's intent. Agent success claims are not an input to the evaluator.

Evidence digests are tamper-evidence for accidental changes, **not signatures or proof against a user with control of the same machine**. The coding adapter only accepts results from the current in-memory `doctor` run and maps them to the operator-sealed requirement-to-script bindings. It does not read a saved bundle back to decide. The saved bundle contains evidence IDs, facts, hashes and statuses, but omits free-form requirement text.

## Current coding workflow

1. Start with a review-only, source-linked draft of the original prompt:

   ```sh
   amabie prompt-evidence draft "Validate email input.
Hash passwords.
Add tests." --json
   ```

   The command emits a JSON request skeleton without changing project files. It preserves the exact goal and proposes candidates at line/list, sentence, comma/semicolon, and conservative action-conjunction boundaries. Each candidate has a full source span plus exact `focusStart`/`focusEnd` offsets; validation checks both the quoted source and the focused text, and source coverage still accounts for every non-whitespace character once. When exact wording repeats, each occurrence must have its own candidate; incomplete duplicate mappings and overlapping matches are rejected as ambiguous. The text view displays exact focus offsets separately from the broader mapped span; with `--json`, stdout remains the request file while stderr records the extractor, lexical coverage, and review notes. The splitter is deterministic and intentionally conservative: it can miss semantic obligations that do not have a recognized boundary. It does not infer clarity or verification criteria. Every candidate is `unclear` and has no criteria, so the draft verdict is always `NOT PROVEN`. Review the split, resolve unclear wording, and add explicit criteria before verification. Save the reviewed JSON as UTF-8 at `.amabie/prompt-evidence.json`.

   For model-assisted candidate grouping, the same command can use a local Ollama model:

   ```sh
   amabie prompt-evidence draft "Implement registration. Reject malformed email addresses. Hash stored passwords." \
     --extractor ollama --model qwen3.5:9b --json
   ```

   This opt-in extractor asks the model only for verbatim source quotes. Amabie rejects paraphrases and ambiguous or overlapping spans, recomputes offsets itself, and still emits `unclear` candidates with no criteria. Any substantive original prompt text outside the model's quotes is added as an exact, source-linked unresolved candidate with a review warning; connector-only gaps are ignored. A deterministic post-processor keeps noun lists introduced by `with`, `including`, or `covering` inside their complete source clause rather than splitting them into context-free fragments. It can split coordinated action verbs it recognizes, with a review note because the actions may still depend on shared context. Every candidate remains `unclear` until a person reviews and adds criteria. The extractor accepts only an unauthenticated loopback HTTP origin, refuses redirects, and uses a bounded response and timeout. Amabie sends the prompt only to loopback; it cannot prevent a local service from proxying data elsewhere. It does not decide whether the candidates are semantically complete or what evidence proves them; operator review remains required.

   For an additional local, review-only preview of possible acceptance criteria and evidence types, explicitly add `--suggest-criteria`:

   ```sh
   amabie prompt-evidence draft "Implement registration. Reject malformed email addresses. Hash stored passwords." \
     --extractor ollama --model qwen3.5:9b --suggest-criteria --json
   ```

   This makes a second loopback-only model call. The JSON output uses `amabie-prompt-evidence-review/1`, with the unchanged request under `request` and separate suggestions keyed to exact draft requirement IDs and source text. The request's criteria arrays remain empty; each suggestion is marked `unreviewed`, is not evidence, and cannot affect a verdict. Suggestions include explicit assumption notes and the model is instructed not to invent thresholds or policies, but its output can still be wrong; inspect every assumption and wording. Unknown or duplicate requirement IDs and malformed suggestion text are rejected. If the model omits a candidate, its preview remains empty. Review the source, criteria, and evidence ideas yourself, then add only the criteria you approve to the request before registration. This mode cannot prove the model covered the prompt or that its suggested checks correctly express user intent.

2. Register that same exact task and each reviewed candidate before work begins:

   ```sh
   amabie task "Validate email input.
   Hash passwords.
   Add tests." \
     --requirement "Validate email input." \
     --requirement "Hash passwords." \
     --requirement "Add tests."
   ```

3. Bind each exact requirement to a check that already belongs to the sealed plan, then seal that declaration through the normal operator workflow. For example:

   ```sh
   amabie bind test --requirement "Validate email input." --reseal
   amabie bind test --requirement "Hash passwords." --reseal
   amabie bind test --requirement "Add tests." --reseal
   ```

   `amabie bind` is the operator’s explicit mapping act. A successful suite does not prove that its assertions actually cover the wording; the relevance of each bound script still needs review.

4. Each requirement entry in the reviewed request has this shape:

   ```json
   {
     "text": "Validate email input.",
     "sourceRef": {
       "kind": "goal",
       "start": 0,
       "end": 21,
       "excerpt": "Validate email input.",
       "focusStart": 0,
       "focusEnd": 21
     },
     "clarity": "clear",
     "criteria": [
       {
         "statement": "A sealed project check covers the email validation behavior",
         "adapterId": "amabie.coding.sealed-plan",
         "evidenceType": "sealed-check-run",
         "predicate": { "path": "/ok", "equals": true }
       }
     ]
   }
   ```

   The request envelope is `{"schema":"amabie-prompt-evidence/1","goal":{"taskType":"coding","text":"<the exact registered task>"},"requirements":[...]}`. The `end` offset is the exact character length of the source excerpt. A `goal` source reference must quote the corresponding exact substring of the original goal.

5. Run the full check plan and request the experimental report:

   ```sh
   amabie doctor --prompt-evidence .amabie/prompt-evidence.json --json
   ```

   The request file must be a regular file inside the project and no larger than 256 KiB. This mode refuses `--check` and `--fast`, because neither can establish complete coverage. A source-map gap prevents `PASS`. A passing result still means only that every *registered, source-mapped and explicitly bound* criterion matched the check evidence; it does not establish that the draft decomposed every compound sentence semantically or that a broad test suite is relevant to every criterion.

6. Optionally run the bounded correction loop with an external coding-agent process:

   ```sh
   amabie prompt-evidence loop \
     --request .amabie/prompt-evidence.json \
     --agent codex \
     --authorize-corrections --json
   ```

   Use `--agent claude` for the Claude Code profile. Both built-in profiles use the same bounded subprocess transport, correction report, and independent sealed-plan verifier; provider-specific CLI behavior does not alter verdict logic. Amabie launches them directly without a shell. Codex receives the report on stdin via `codex exec -`, with ephemeral session state, an explicit `workspace-write` sandbox, and `approval_policy=never` because the loop has no interactive approval broker. The sandbox remains active; this does not use full access or Codex's automatic reviewer. Claude Code runs in print mode with session persistence off, at most six turns, and `--restricted`, which confines file tools to the working directory, loads only managed or explicitly supplied settings, and removes command-running tools. Only built-in file/search tools are allowed; `--strict-mcp-config` is used without an MCP config, and permission requests that would require a prompt are denied. Built-in profiles pass an allowlisted environment with OS, executable-path, and saved-login locations; ambient API keys, provider tokens, routing URLs, and unrelated cloud credentials are omitted. Saved CLI credentials remain available to the provider CLI itself.

   The Claude Code profile requires CLI version **2.1.248 or newer** because that release introduced the required `--restricted` mode ([official CLI reference](https://code.claude.com/docs/en/cli-usage)). Before sending a correction report, Amabie runs a bounded `claude --version` preflight (10 seconds, 4 KiB output limit) and stops without sending the report if the command fails, its version cannot be parsed, or the installed version is too old. This check makes no model request and is not an isolation boundary. The tested local CLI is 2.1.278 and its help exposes the required flag.

   This remains an explicit experimental action. `--authorize-corrections` is mandatory because the selected agent can change project files. Amabie runs the complete sealed plan before correction and invokes a fresh full `doctor` run after a Git-visible project change. Each correction process is capped at five minutes, each verification run at 30 minutes, and the loop at three attempts. It stops on no change, process failure/timeout, or a changed request, registered task, sealed plan, or Amabie CLI. Agent output and completion claims never count as evidence. CLI use can consume a provider subscription quota or usage-billed API allowance; Amabie does not set a provider spend cap, so obtain the operator's approval before starting any run that may incur charges. Authentication status checks and CLI help do not make model requests.

   **Working-tree safety limitation:** the correction process edits the current project working tree directly. The loop does not isolate edits into a disposable copy or automatically roll them back when the agent fails, times out, makes no detected change, or verification remains `NOT PROVEN`. The profile prompt narrows the requested work, but it is not a per-file authorization boundary. Change detection hashes `HEAD` and Git-visible tracked/untracked paths; ignored-file-only changes are not detected as correction progress. Until transactional correction is implemented and verified, use a disposable/reviewable Git worktree, keep unrelated changes out of it, and inspect the diff after every run. This limitation does not turn missing evidence into a pass, but edits can remain in place after a blocked result.

   These profiles do not upgrade `LOCAL` to `HARDENED`. The processes still run as the current OS user in the subject project, and project content sent to Codex or Claude is handled by that provider under the CLI account's data and billing terms. Codex `workspace-write` is its CLI sandbox policy, not Amabie's independent isolation. The custom `--agent-executable` escape hatch remains for deterministic fixtures and operator-supplied adapters; custom processes inherit the caller's environment and receive the structured JSON on stdin, so treat them as fully trusted.

   The earlier local Aider adapter is retained as a test/reference integration, not the primary agent architecture. It accepts only explicit project-relative regular files and loopback Ollama model configuration; its constraints and invocation remain documented in its source and E2E harness.

   ```sh
   amabie prompt-evidence loop --request .amabie/prompt-evidence.json \
     --agent-executable node \
     --agent-arg tooling/agents/aider-correction-adapter.mjs \
     --agent-arg src/auth/register.ts \
     --agent-arg test/auth/register.test.ts \
     --authorize-corrections
   ```

   The adapter remains opt-in and experimental. Its explicit file context and cleaned process environment reduce exposure, but do not form an OS sandbox; the outer Amabie process and adapter still run as the current OS user. Amabie independently reruns the full sealed plan and can still return `NOT PROVEN` when a separate release or regression obligation lacks evidence.

## Verifier and correction contracts

The shared package `@amabie/prompt-evidence` is task-neutral. It defines goals, source-linked requirements, criteria, verifier adapters, evidence records, deterministic evaluation, per-requirement statuses, and structured correction reports. The production adapter implemented here is `amabie.coding.sealed-plan`, which consumes fresh sealed-plan results. A document-outline mock uses the same contracts in tests to check extensibility; it is **not** a document-agent integration and does not count toward Phase 3.

The core correction controller remains task-neutral. The CLI now supplies an opt-in process adapter for coding agents: it sends the structured report over stdin, does not parse the agent's claim as proof, requires a Git-visible change, and gathers a new report from a full child `doctor` invocation before the core re-evaluates evidence. A deterministic process fixture covers the false-done scenario. A separate live local-model run uses the test-only Ollama agent in a temporary Git project: Qwen 3.5 9B received the original goal, one independently `unmet` requirement, and the designated file, then corrected it in one attempt. The P2E subreport passed 2/2. The enclosing `doctor` stayed `NOT PROVEN` because the sealed baseline already passed the same check, leaving the separate `regression-evidence` obligation unproven. The run used 3,778 prompt tokens, 17 response tokens, and 53.344 seconds of local inference. It made no remote model call. This is evidence for the generic process bridge with a constrained local model agent, not a live Codex/Claude CLI run. Codex CLI with the local provider was also tried, but in the temporary profile it downgraded `workspace-write` to `read-only`; it made no change and Amabie correctly stopped the loop.

To repeat the local-model run, start the installed local model server and run `node tooling/test-support/prompt-evidence-local-agent-e2e.mjs` after the project build. The script defaults to `qwen3.5:9b`, sends requests only to a loopback Ollama endpoint, and creates a disposable synthetic Git project. It is an opt-in validation harness, not part of the stable CLI or the default test suite.

The available local Kai decision MCP only classifies requests; it does not generate requirement text. In one advisory domain probe, it classified a registration/validation/password-storage/tests prompt as `documents` with 0.22 confidence. This single probe is not a model benchmark, and its output was excluded from requirement drafting and verdicts.

## Known limits and release boundary

- The default candidate extractor uses conservative deterministic boundaries. Optional local Ollama extraction can group exact source quotes. The separate `--suggest-criteria` mode can draft possible criteria and evidence types, but those untrusted ideas never populate the request, become collected evidence, or affect a verdict. Suggestions can still introduce unsupported assumptions or miss requirements. Its numeric-source warning flags digit-form numbers absent from the original prompt; word-form values and nonnumeric unsupported choices can evade it, so this is not semantic validation. Neither mode establishes semantic completeness. Lexical source coverage detects omitted source text, not whether a model grouped it correctly. When two unique, non-overlapping source quotes are separated by a recognized dependent-clause marker, the Ollama path merges them into one exact contiguous candidate and emits a review note. Other incomplete phrases and incorrect groupings remain possible, and a merge can combine multiple obligations. Every candidate and every verification criterion requires operator review before the request is registered and bound.
- The `clarity` and criteria fields live in the local request file. This prototype has no separate authenticated human-approval record; the operator must inspect the exact requirement split and criteria before running the gate. A same-user process can modify local request files, consistent with the documented `LOCAL` boundary.
- The current CLI adapter uses a sealed script's exit result as evidence. It does not inspect individual test assertions or prove that a script semantically covers its mapped wording.
- The Ollama extractor allows only loopback origins and refuses HTTP redirects, with a local regression test proving a redirect target receives no prompt.
- Only the coding adapter executes against real Amabie checks. The document adapter is a mock; Universal Agent Assurance remains future work.
- The correction process bridge has one successful local Aider/Ollama CLI E2E and one successful live Codex CLI correction E2E. Claude CLI correction remains unvalidated. The general bridge inherits the caller's operating-system authority and may read or modify files outside the project or access the network. It is not an OS sandbox or filesystem security boundary; invoke only an executable the operator trusts. The E2E's isolated environment and provider workspace settings are test-harness controls, not an Amabie security boundary.
- The prototype does not change LOCAL capability semantics, enable HARDENED, or provide a cryptographic signature over locally stored evidence.
- No experimental behavior is enabled by default. The new command mode is explicitly invoked, and the report is attached to that fresh doctor run.
